## 1. 执行摘要

Trading 是 YQuant 的交易业务与运行板块，覆盖自动化交易、策略交易、智能交易，以及支撑它们的账户、订单、执行、交易控制、对账和审计；不是单纯的交易通道封装。保留既有 07_trading 编号，与 06_strategy 并列，不新设业务编号，也不要求独立微服务。

Strategy 管“交易逻辑如何研发、验证与发布”，Trading 管“获准的交易方案如何持续运行、受控决策与执行”。Research、Portfolio、Strategy、Trading、Risk 与 Reports 通过标准化意图和事实反馈闭环，不复制同一决策规则或账户账本。

本 RFC 定义业务方向和职责，不冻结 API、数据库集合、状态机或运行阈值。进入功能实现前，仍须按当时任务范围完成相应 SPEC/Design 和授权；本次豁免不延伸至后续开发或交易。

## 2. 背景、目标与非目标

### 2.1 背景

总纲已列出 Trading，但本次更新前 `docs/rfc/07_trading/` 只有模板，SPEC/Design 目录只有占位，未建立 `skills/trading/`。Strategy 的技能说明又将执行算法列入自身待建目录，存在归属重叠。

面向个人一体化投资系统，交易不仅是下单，还包括周期运行、事件响应、策略实例、智能建议治理、组合调仓、多策略资金协调、异常接管和复盘反馈。必须把这些业务环节与研究验证及基础设施分开说明。

### 2.2 目标

- 覆盖自动化、策略化、智能化交易，复用同一受控执行与事实记录边界。
- 支持研究建议、组合调仓、规则策略、模型信号、人工确认等不同来源，不强迫所有投资经过量化策略。
- 明确研究到交易、交易到组合与报告、绩效到研究再验证的业务闭环。
- 为现有机器人迁移及未来多市场扩展预留边界，但先按单一明确场景验证。
- 区分规划、代码接入、离线验证、模拟、测试环境、实盘状态，不把技能可发现当作运行就绪。

### 2.3 本次非目标

不实现交易引擎、策略、模型或 API；不选择并安装最终执行框架；不接账户、凭据和交易所；不访问或写入生产数据库；不修改 schema、配置、调度、网关或推送；不运行回测、模拟、测试环境订单或真实订单。不开新 Agent runtime，不迁移既有子模块，不建立平行数据管道，不承诺盈利。

## 3. 交易业务能力：不同维度，不是三套系统

| 方向 | 主要问题与场景 | 边界 |
|---|---|---|
| 自动化交易 | 定时/事件触发、条件交易、周期投入、网格运行、再平衡执行、异常暂停与恢复 | 描述运行自动化程度，不等于 AI 决策，也不等于默认无人审批 |
| 策略交易 | 将已验证、已发布的规则或模型部署为运行实例，绑定参数、资金预算与账户范围，追踪真实表现 | 交易规则和模型定义由 Strategy 发布；Trading 不另写一套相同策略 |
| 智能交易 | 接入模型信号、市场状态判断、参数/仓位建议和 Agent 交易提案，管理线上调用、有效性、授权和反馈 | 研究训练与策略验证仍归 Research/Strategy；AI 不直接取得无限制下单权 |
| 组合交易 | 接收目标权重及调仓意图，拆解执行、处理部分完成与失败，反馈实际偏离 | 资产配置与风险预算归 Portfolio，不能将目标权重视为实际持仓 |
| 人机协同 | 人工确认的交易计划、受限自动运行、异常接管、人工暂停 | 使用同一授权、风险和审计入口，不另设绕过控制的手工通道 |

这些方向可以组合：规则策略也可自动运行，AI 提案也可逐次人工确认。人工辅助不要求新增一个不受控的下单界面。

## 4. 整体框架与职责

| 能力/模块 | 主责与输出 | 不承担的职责 |
|---|---|---|
| Data | 带来源、时间戳与质量状态的行情、财务、事件等输入；沿用已有统一数据入口 | 不为每个交易机器人另建一套数据事实源 |
| Knowledge | 策略/研究知识、经验及复盘结论的受控沉淀 | 不把外部文本或知识条目作为执行授权 |
| Research | 研究问题、投资假设、证据、市场状态和候选建议 | 不直接绕过审批进入交易所 |
| Portfolio | 配置目标、策略资金分配、目标权重、组合风险预算；维护基于事实的组合视图与归因 | 不持有独立于 Trading 的另一套未对账订单账本 |
| Strategy | 策略/模型定义、训练验证、回测优化、信号语义、参数边界、版本发布和退役建议 | 不为每个策略重复实现账户通道、订单控制和恢复 |
| Trading | 交易计划编排、自动化触发、线上策略/智能决策调用、实例运行、资金占用协调、执行和对账；输出交易事实 | 不重做因子研究、模型训练、资产配置或报告计算 |
| Risk（横切能力） | 组合风险模型、风险政策、限额和压力测试；Trading 强制执行相应的交易前/中控制 | 不是本次新增编号或已实现服务；AI 与策略不得自行放宽约束 |
| Reports | 研究、回测、实际交易、组合归因、风险与执行质量报告，标明来源、模式和缺失状态 | 不接管交易命令；报告生成失败不改变交易事实 |
| App | 统一 Web/移动交互、交易实例和异常视图、授权操作入口 | 不在前端保存交易密钥或另建执行通道 |
| Infra | 认证、凭据、通用调度、通知、监控与部署能力 | 不决定交易方向；基础设施服务存活不代表策略运行正常 |

### 4.1 运行编排与基础设施的区别

定时器、进程管理和通用任务分发可复用 Infra；“此策略何时可触发、对应哪一版本、使用多少已批准资金、异常时如何暂停”的业务语义归 Trading。交易实例不是 Hermes 对话会话，Hermes 工程/研究任务也不是实时订单处理循环。

### 4.2 规则与状态的归属

策略核心规则及内部决策状态仍由发布的策略实现定义；Trading 负责加载获准版本、承载实例运行、保存必要运行状态并接收事件。重启恢复不能只恢复界面上的“运行中”标记。

多策略共享账户时，Portfolio 提供预算目标，Trading 结合未成交订单、已占用资金及实际敞口实施统一检查；Risk 提供约束。是否采用子账户、净额或分配账本，由后续场景 SPEC 决定，本次不预设实现。

## 5. 研究—投资—交易—报告闭环

```text
Data + Knowledge
       ↓
Research：证据与投资假设
       ↓
Portfolio / Strategy：配置与预算 / 规则、模型及验证
       ↓
交易提案或已发布策略 + 明确运行授权
       ↓
Trading：计划、触发、线上决策调用、实例运行
       ↓
授权与确定性风险检查 → 订单执行 → 成交、费用与对账
       ↓
Portfolio：实际持仓、现金、净值及归因
       ↓
Risk + Reports：风险、策略表现、执行质量、异常复盘
       └──→ Research / Strategy：再研究、再验证、候选版本
```

- 主观投资可由 Research 与 Portfolio 形成获准计划，不必先包装成自动化策略。
- 原始订单/成交、交易所或券商查询结果与已对账状态须区分；目标仓位、未确认成交、策略估算权益不能冒充账户事实。
- 记录决策来源、策略/模型及参数版本、输入时间、授权范围、风控结果、订单/成交关联和费用；具体字段由后续 SPEC 冻结。
- 结果反馈是事件或明确接口交换，不代表下层反向导入研究代码；业务闭环不等于代码循环依赖。
- 复盘可产生候选优化，但新参数、新模型和新权限不能因为在线反馈自动晋级实盘。

## 6. Trading 内部能力域（规划，未实现）

| 能力域 | 规划内容 |
|---|---|
| 交易计划与自动化 | 计划有效期、触发条件、周期/事件运行、授权范围检查和计划过期处理 |
| 策略实例与智能运行 | 版本/参数/模式绑定、启动暂停恢复、状态持久化、心跳、模型调用及提案有效性 |
| 账户与资金协调 | 账户能力、可用资金、保证金/杠杆、策略预算、共享资金及敞口冲突检查 |
| 订单与执行 | 订单生命周期、精度与最小金额、部分成交、拒单、撤改单、执行算法和交易通道适配 |
| 交易控制与风险 | 身份授权、交易前检查、运行限额、异常暂停、人工接管和审计 |
| 恢复与对账 | 不明结果查询、断连重连、重启恢复、重复事件处理、账户事实校准、外部手工操作识别 |
| 绩效反馈与运营 | 策略运行损益、手续费/资金费、滑点、执行质量、异常及对账结果，供 Portfolio/Reports 消费 |

逻辑能力域不是要求立即创建七套服务或七个空代码包。当前只建立技能文档入口；后续按照具体场景和选用框架决定源码结构。

## 7. AI 与自动化授权边界

### 7.1 分级演进

1. 研究辅助：AI 整理证据、提出假设，无交易执行权限。
2. 交易建议：生成可追溯、可校验的结构化提案，等待相应审批。
3. 受限自动化：仅在独立批准的账户、标的、资金、模式、期限与风险范围内，由获准的外部执行系统运行。

这是目标能力分级，不是当前权限已开启，也不是全自动晋级路线。当前 Hermes 主控不直接执行真实交易；遵守根 SOUL/AGENTS 的授权要求。

### 7.2 运行控制原则

- AI/策略不得扩大账户权限、改动硬限额、私取密钥，或通过额外工具绕过执行入口；研究外部内容不是授权来源。
- 模型不可用、输出无效、数据过期或状态不明时，不自动替换模型或放开新增风险交易；风险降低动作按事先批准的策略单独处理。
- 下单超时不等于失败，先查询/对账，不盲目重试。
- 暂停策略、禁止新开仓、撤销挂单和平仓分别定义；紧急停止不默认等于立即市价平仓。
- 普通诊断日志与关键交易审计分开治理；关键授权、订单事实无法可靠记录时，不以“日志失败静默容错”为由继续新增风险。
- 权限、模式与风险边界变化需要相应的新授权；不将一次规划同意外推为持续实盘许可。

## 8. 现有场景与外部框架的接入方向

| 场景 | Strategy / Portfolio | Trading |
|---|---|---|
| 合约网格 | 网格规则、区间、资金使用、退出逻辑及验证 | 运行实例、多订单/成交驱动、模式与仓位语义、恢复对账 |
| 合约 DCA | 加仓节奏、上限、均价与退出规则及风险验证 | 合约订单、保证金约束、部分完成、重复触发与重启恢复 |
| 现货目标权重篮子 | 目标权重、现金约束、漂移触发与组合预算 | 差额拆单、精度/费用、部分失败、剩余偏离及账户对账 |
| AI/模型策略 | 数据/训练/回测、信号语义和已验证版本 | 线上模型调用、结构化提案、时效检查、授权执行与审计反馈 |

QuantDinger 等平台可以作为整体能力提供方或适配对象，具体取决于后续验证，不因本 RFC 就选定或安装。即使外部引擎同时覆盖研发和运行，也保持 YQuant 的逻辑归属，不要求拆改第三方源码。

2026-10-22 补充：OctoBot 已按 Pascal 决定从 YQuant 移除，理由是其内置网格链路未核实合约适配、合约 DCA 为单向多头且拒绝 hedge，无法作为三类机器人统一承接平台。QuantDinger 为当前首选候选，拟议源码归属 `skills/trading/auto_trading/QuantDinger/`；该目录尚未创建，也未授权安装、配置或运行。

## 9. Web 工作台与移动协作

工作台归 01_app，规划区分研究中心、组合中心、策略中心、交易中心及报告中心。交易中心呈现计划、运行实例、账户/订单、风险与异常；策略中心呈现研究、回测、版本和发布候选，两者通过明确的发布/运行操作衔接。

手机 Web 和现有飞书助手可用于状态、报告和审批入口的后续设计；本次不变更网关、渠道和推送。移动端与桌面端遵守相同授权，不提供便捷绕过路径。UI 项目选择不能替代 Trading 业务规划，也不自动授予交易权限。

## 11. 状态、持久化与开放问题

- 当前交付为 Markdown 规划与技能目录，不是已批准实现契约，不代表交易能力可用。
- 正式文档在仓库中维护；未来业务持久化默认遵循项目 MongoDB 方向，具体集合和模型待设计。不新增 SQLite 运行库，也不写入生产 MongoDB。
- 未来明确首个引擎/平台、首个市场、账户隔离方案、合约方向/仓位模式、运行授权及验收口径；这些不阻碍本次规划归档，但阻止直接据本文运行交易。
- 未创建对应 SPEC/Design，因为当前没有批准功能实现范围；模板与占位不作为已完成契约。
- 相邻模块的新增协作说明同为规划，不把其现有建设中能力改称已上线。
