# Worker 异常的最小恢复

适用于 Kanban worker 的预算耗尽、崩溃、模型额度限制、审批拒绝和未完成交接。目标是保留实物与可信证据，只恢复尚未完成的 delta，不默认重建任务链。

## 当前规则优先（2026-11-14） <a id="current-rules"></a>

- 本技能及原有 `references/` 的唯一维护源为项目 `skills/infra/worker-budget-recovery/`，frontmatter name 不变，不保留 profile 同名副本；修复链配套见项目 [yquant-kanban-repair-orchestration](../yquant-kanban-repair-orchestration/SKILL.md#current-rules)。
- 后续新任务服从 [AI Coding Pipeline 统一 Validate](../ai-coding-pipeline/SKILL.md#unified-validate)：仅 Full / Light，独立 `yquantreviewer` 同时负责测试、消费者/反例审查和裁定，tester 非默认；Full 仍有 RFC/SPEC、Design 两阶段及三份独立文件。下文及 references 的 Verify/Review 旧称与分离链仅保留旧任务兼容，不默认新增阶段。
- 新任务的目标、范围、计划、负责人、依赖、进度、状态与交接摘要只在 Kanban，不创建或维护 `data/tasks/`、正文镜像、逐卡全文 handoff 或重复 Closeout 报告。下文及 references 中这些强制存档步骤仅属旧任务兼容，非新任务指令；原失败与历史证据不删除、不改判。小任务 Kanban 结论与必要日志，复杂任务一份验收报告及原始证据；目录按目标项目 AGENTS，YQuant 为 `data/reports/YYYY-MM-DD-short-topic/`。当前 profile scratch 仅临时探针/中间文件，不作第二状态源。
- 保留“先核实物与证据、只恢复剩余 delta”的方法；只缺登记则复用仍适用证据，真实验收缺口不得补写 PASS。使用原生 `kanban_*` 工具优先，状态写后读回精确目标；旧命令、配置/模型/认证/生产恢复示例不授予本卡或未来任务权限，卡面与 runtime 均须允许，安全拒绝停止对应动作、不换形态重放。
- `kanban-orchestrator` / `kanban-worker` 保留为原生技能名称引用，按实际发现加载；`kanban-verification` 为主控 profile-local 配套，不假定 worker 可见。新任务必需规则以内联卡面及本项目现行契约为准，不伪造项目内路径、不为发现限制迁入第三个技能。

## When to Use

- 收到卡片的 blocked / triage / gave-up / rate-limited / “needs attention” 通知，需要判断是代码失败、流程偏离还是外部通道问题。
- worker 未完成交接：产物齐全但漏收尾，或产物残缺需要收窄续接。
- 需要判定能否行政收尾（而非重跑），或需要把已知生产输入 HOLD 与可分离离线工程拆开。
- 参考：`references/candidate-contract-spot-checks.md`（恢复前的候选契约抽查；含分页检查点失链、部分写入与单引用CAS恢复步骤）。
- 参考：`references/bounded-continuation-batch-ledger.md`（主控接手后的有界续批账目：每批字段、只读快照纪律、停止/续批判定、对外表述口径）。

## 1. 先核实当前状态，再解释通知

1. 用 `hermes kanban show <task-id> --json` 读取当前状态、parents、最近 run、summary/comments；用 `hermes kanban log <task-id> --tail <字节数>` 查看对应执行尾部。优先精确读原卡及已知 Gate，不展开整板长正文。需要解析大 JSON 时，在尚未遭到相关拒绝前，用 CLI 直接重定向到当前 profile 的 scratch 文件，再单独解析原始文件；工具自动保存的截断展示日志不保证仍是合法 JSON，不能把解析失败当作看板损坏。相关命令若已被拒绝，先取得新授权，不用重定向或文件解析替换来复现被拒动作。
2. 将通知与最近 run、最新 event 及其 actor/comment 对齐；旧标题、旧 blocked/gave_up 通知可能晚到。通知中的“will retry”不是调度事实，以当前 status 和是否出现新 run 为准。最近 run 的新拒绝仍须处理，不能只因卡片暂显示 running 就称通知过时。worker_pid 是历史字段，不单凭它宣称进程活跃。
   - 若通知对应主控刚写入的 block/comment，且没有新 run、产物变化或新决策，只读核验后简短说明“本次登记触发的通知，无新增故障”；不再次 block/comment、建卡、重跑测试或重发整份进度。重复状态写入会触发新的通知，形成自激反馈循环。
   - 给分片错误归属到具体批次前，核对 `last_attempt_at` / `updated_at` 与该批执行时间；现存旧错误标记不是本批新增失败，不能只凭错误码仍在库中就重开修复。
   - 若超时卡尚未分类且确有待裁定输入，先核对没有活跃新 worker，再通过受支持命令 `hermes kanban block <task-id> --kind needs_input '<具体未闭合项>'` 原地登记，并用 `hermes kanban show <task-id> --json` 读回；不要仅靠通知措辞决定恢复。
3. **先查拒绝，再选择校准执行。** 在执行尾部之外，定向检索该 run 的完整日志中 `BLOCKED` / `denied` / 审批停止记录；预算耗尽摘要可能省略更早的拒绝。按动作语义关联拒绝前后记录，不只比命令字符串：把被拒内联探针写成 scratch 文件、再由 `python` 或 `pytest` 执行，仍是继续等价动作，不因换成测试入口而获得授权。分别记录「原动作未执行」「后续动作实际证据」「流程偏离」，不因后续成功追认授权，也不由主控再执行同等动作验证；先取得明确恢复授权。若恢复中的活跃 worker 再次违反已批准边界，使用受支持的 `reclaim` 停止该 worker，随后 `block` 防止重派，并读回终止事件与当前状态；保留候选、失败日志及旧 run，不用再次追加相同警告后原样解锁。进度查询发现此情况时先报告实际暂停，不以心跳正常宣称执行健康。
4. 读取实际产物和独立报告，区分剩余工作是代码、验证、报告还是状态登记；没有完整原命令/结果/基线证据时，不把自报成功当 PASS。对 `retries exhausted`，核对实际 runs 数及当前 CLI 的 `max_retries` 语义；失败熔断阈值不一定等于额外重试次数，不能据通知声称已重跑多轮。
5. 用户查询运行中进度时，先读当前卡、最新 run 的短日志和该 run 已保存的测试输出，报告带时区的快照、已落代码与已验证增量、当前工作及剩余项；不要为汇报另起全量回归或扰动活跃共享树。将定向测试、修改前的中途全量结果和最终候选结果分开，不累加重复轮次、不把旧报告标题或累计 git diff 归为本轮新增；worker 继续编辑后，旧全绿仅作历史基线。
   - **用户催办时，把必要取证和最小恢复合并完成再简短汇报**：先精确核对当前卡、最新 run 的拒绝/失败原因及实际产物，再选行政收尾或同卡窄续接；不得跳过这些前提直接 unblock。需要恢复时按 edit → 完整读回正文/依赖/状态 → unblock → dispatch 一次 → 读回新 run 的顺序执行，不能把读回与解锁并行。去掉无依据的整板检索、重复测试和重复进度长文；简报只写新增产物、当前真实阻塞、已执行动作和剩余交付，不用重派/PID冒充工程增量。
   - **进度汇报不要替下一阶段预支结论**：独立 Verify/Review 未落盘 verdict 前，只能说「技术上倾向 X、报告未落盘」，不能写成「X 已通过」；也不能只凭心跳/耗时宣称快完成。

## 2. 按原因选择最小恢复

| 现场证据 | 恢复方式 |
|---|---|
| 预算耗尽，但独立验收与正式 PASS 报告已完整落盘 | 核对候选和验证输入未漂移后，按 kanban-verification 的行政收尾规则登记；保留旧 run，不重复执行，也不冒充主控取得了 Tester 证据。 |
| Design/交接已落盘，但正文判定 BLOCKED 且列出真实契约或输入路径缺口 | 将执行超时与内容门禁分别记录；文件齐全不等于验收齐全，不能按“漏 complete”行政授予 PASS。复用已完成设计，只裁定列明缺口，不重跑整份探索、不放行依赖实现。既有修复授权继续有效；新增文件范围、生产加载或取数通道只列各自必要决定，不重复申请同一修复授权，也不默默缩减原验收。 |
| 预算耗尽，**四步产物齐全但 worker 漏了收尾调用**（最后一步没调 comment/complete） | 先由主控**逐项独立核验产物**（每个步骤的真实输出文件、时间戳、关键字段），确认四步均已实际发生且结论自洽；确认后**行政收尾**（comment 记录四步证据 + complete 写清指标与副作用），**不重跑 worker**——重跑会产生重复提交（重复 job / 重复回测），且往往再次耗尽预算。 |
| 预算耗尽，测试证据已落盘但**正式验证报告未写** | 先区分缺的是裁定还是索引：正式 PASS/APPROVE 与逐项裁定尚未由独立角色落盘时，原地收窄同卡，让该角色只写报告和收尾；主控不得代写裁定性报告。已有正式独立报告且只缺交接/状态时，主控可补纯索引并行政登记，注明真实验证作者和登记者。两种情况都复用适用的原始证据，不重跑已完成步骤，也不因 summary 自报成功而授予 PASS。 |
| 预算耗尽，**结论已在 run 的收尾摘要里给出、但报告/交接未落盘** | 这是上一行的变体，但结论不在磁盘而在 run 尾部（框架会打印 "asking model to summarise"，摘要含技术结论 + 自认缺口）。处置：① 先用 `hermes kanban log <id> --tail <字节数>` 读到那段摘要，把它当作该角色的权威结论输入；② 原地把同卡正文收窄为**只剩落盘**（写报告 + 写交接 + 补/改证据目录 + comment + complete），并明写「结论沿用你上一轮的裁定，不得重做论证、不得重跑已跑过的测试」；③ **不要由主控代写该角色的裁定性报告**——那是角色分离的实质破坏；主控只能补写纯索引型交接文件（产物清单 + 命令 + exit + 计数），且不得改写判定方向或任何计数；④ 报告里引用的每个证据文件必须逐个确认存在，见下条。 |
| 证据目录 README 列出的文件**实际并不存在** | worker 常在预算耗尽前写下 README，列出计划中的 N 个证据文件却没来得及生成。收窄续接前先 `search_files`/目录列举逐个确认哪些真实存在，并在正文里点名「README 列出的 X/Y/Z 尚不存在」；禁止报告引用不存在的文件，也禁止 worker 声称已生成。要么允许补齐（重跑一次已获准的只读离线命令并重定向落盘），要么按实际落盘内容改写 README 并在报告中说明证据位置——不允许两边都留成互相矛盾的表述。 |
| 预算耗尽，仅缺报告或有限检查 | 原地收窄同卡 body：已完成项、唯一剩余 delta、可执行命令、明确终止条件与交接预算；不要从最初范围再跑一遍。 |
| **实现已落盘且可用，但卡未收尾（无报告/无 complete）** | 先由主控**独立核验候选**（编译、回归全绿、契约形状、候选哈希、行数），再把续接正文写成「已落盘内容 + 唯一剩余 delta + 禁做事项」；明确写出“不得重写已实现部分”。这样续接 worker 只需做增量，不必重建。 |
| 墙钟超时（`elapsed ... > limit ...`），候选已落盘但修复后测试/交接未完成 | 先核对最新 run 和精确 PID，确认没有新 worker 同时写共享树；主控运行原卡冻结回归并保存候选哈希。若全绿，将同卡收窄为“核对哈希 → 固定测试与 scoped diff → comment/complete”，禁止重读全模块或重写实现，再恢复。保留原超时 run 和既有下游独立 Verify；主控校准只用于选择恢复路径，不是 Tester 验收。 |
| 墙钟超时，**已落盘产物完好**（语法/编译通过、diff 在 allowlist 内、缺的是文档/交接/测试收尾） | 超时 ≠ 工作失败。先由主控**独立核验产物**（`git status --short --untracked-files=all`、scoped diff、语法/编译、交付物是否落盘），再用**steer comment** 把重试拉成“续做”而不是“重做”：逐条列出已改文件、已核验事实与其产出命令、已确认的实现要点（防止重写正确代码）、以及唯一剩余 delta。**不重建卡、不换 assignee、不改范围**。dispatcher 自动重试产生的新 run 是“继续”不是“重新开始”——两者对用户的表述不同，不要合并成一句“已重启”。 |
| 墙钟超时，**产物残缺**（缺关键实现文件、测试未跑、交付物不存在） | 这才是真正的未完成。按真实产物重建卡正文：把已核实的只读结论内联（基线测试计数/exit、API 白名单、模板结构）并标注核实者，**显式禁止 worker 重跑这些核实**；给定向读取次数上限；写明墙钟纪律与“交接优先于完美交付”。重建的是同一张卡的范围，不扩大。 |
| 同一卡收窄后再次超时，仍仅留下测试或少量候选，主体实现缺失 | 停止原样解锁整包任务；按真实产物拆出可独立验证的下层实现，原卡原地收窄为集成与完整收口。先创建下层卡，再将其真实ID设为原卡parent，更新原卡正文并读回，最后恢复原卡；下层未done时原卡应为todo，既有Verify/Review仍串接原卡。复用已落盘测试，不再从基线探索或重写测试开始；拆分只是调度恢复，不代表工程通过。 |
| 候选已落盘但实现卡只剩测试/文档/交接等固定尾巴 | 先由主控独立核验候选（编译、既有回归全绿、白名单/契约形状、候选哈希、行数），再把续接正文写成**唯一剩余 delta 的清单 + 精确行号 + 禁做事项**；不要求 worker 重读全模块或重写实现。 |
| worker 把时间耗在整篇重读/全库探索上而超时 | 续接正文直接给出**已定位到行号的改动点**（原文行号 + 期望语义 + 必要片段读取范围），并显式禁止整篇读取、全库 grep、重新核验已确认源码。 |
| running 且心跳正常，但已定位的小修仍零编辑、反复声称上下文明确后继续读取 | 不必等墙钟耗尽才干预。先用当前 run、限定执行日志、API 耗时和开工快照证明是无产出探索，而非测试、审批或失活进程；有新拒绝则走授权停止分支。无新拒绝且恢复仍在原授权内时，归档旧正文，把已确认行号/语义和唯一剩余 delta 内联到原卡，读回精确一致，再用支持的 reclaim 终止旧 worker 并恢复同卡；保留模型、独立下游和历史 run。读回终止结果与新状态，ready 只称排队，不把重启当产品进展；有部分产物时先校准并明确禁止重写，不盲目零起点重跑。 |
| 同卡已两次收到明确澄清 comment（权威定义＋行号已给全）仍零编辑，继续自行检索"更权威措辞"或历史会话 | 停止继续 comment——多轮澄清无效说明卡面正文已被新旧指令混杂污染，恢复同卡不如换卡：`reclaim` 释放 live claim → `complete`（result 写已核验产物清单与遗留去向）冻结旧卡 → 派极小执行卡，正文只含唯一剩余 delta 的**精确答案**（改动前后代码原文、期望值与预期 zone、禁做任何检索/调研/git 历史考古），不留需要 worker 自行裁定语义的空间；`complete` 报 "a live worker is running it" 时先 `reclaim` 释放再收口，不走 `--force` |
| 墙钟超时且零文件落盘，时间耗在必要的只读前置核实（基线测试、API 白名单、模板结构）之后 | 核实结论有效而非浪费：主控复跑关键项后，把已核实事实连同证据直接内联进续接正文并标注核实者与来源，显式禁止重跑这些核实并给定向读取次数上限；恢复同一张卡，范围/allowlist/下游均不变。 |
| 大量卡反复以 `Reached maximum iterations (N)` 结束、需多次重派 | 先查 profile 的 `agent.max_turns`：Kanban worker 以 `hermes -p <profile> chat -q` 启动，读的就是这个键（`delegation.max_iterations` 只管 delegate_task 子 agent，`goals.max_turns` 只管 goal 模式，二者都与此无关）。统计碰顶率：`~/.hermes/kanban/logs/t_*.log` 中 grep `Reached maximum iterations`，再 join `~/.hermes/kanban.db` 的 tasks.assignee。经用户批准后，只改各 profile `agent:` 段下那一行 `max_turns`：先备份；不能用 sed 全局替换，因为 `goals.max_turns` 同名；改完逐个 diff（应只有 1 行变化）+ `config check`，再用 `HERMES_HOME=<profile> venv/bin/python -c 'from hermes_cli.config import load_config, resolve_turn_limit; ...'` 读回解析值。不要用 `from cli import CLI_CONFIG` 来探测，那会启动交互式 CLI。改动对下一个新 worker 生效；gateway 每一轮都会重读，无需重启。2026-11-06 已统一为 150。 |
| worker 迭代预算耗尽（60/60）但实现主体已落盘且测试只剩个别失败 | 主控独立复跑冻结测试拿到精确失败，定位到行后把同卡 body 收窄为「精确到行的修正清单 + 一次冻结测试 + 交接 + complete」，再恢复派发；不拆新卡、不重写已验证增量。核验失败是否与冻结契约矛盾：若新断言与改动前行为冲突，恢复的是原行为，不是保留漂移。 |

### 迭代耗尽后按技术栈拆卡：下层实现卡 + 上层收口卡

一张 Implement 卡同时跨两种技术栈（例：Python 工具层 + Rust 引擎层）时，worker 撞 `max_turns` 的概率远高于单栈任务——它会在两套上下文、两套测试命令、两套文件规模之间反复切换。恢复方式是**保留原卡 ID 拆成两层**，而不是整包重跑（重跑会重复产出，且大概率再次撞同一堵墙）。

执行顺序（每步单独执行并读回）：

1. 主控先独立核验候选：编译/静态检查 exit、测试计数与失败清单、每个候选文件的 sha256 与行数、allowlist 越界扫描。核验结果写进两张卡的正文，标注「主控已复核，禁止 worker 重跑」。
2. 建下层卡：`kanban create "<标题>" --assignee <profile> --parent <design卡> --workspace dir:<abs> --body-file <镜像.md>`，正文只含该技术栈的 allowlist、已定位到行号的缺陷清单、精确命令与停止条件。
3. 把下层卡接成上层卡的 parent：`hermes kanban link <下层卡> <上层卡>`。参数顺序是 parent→child；写反会把错误卡片降级。
4. 用 `kanban edit <上层卡> --body "$(</绝对路径/镜像.md>)"` **整体替换**上层卡正文（不是追加相反指令），正文写清「禁止推倒重写已落盘部分 + 唯一剩余 delta + 禁做事项 + 已被拒绝且不得重跑的动作」。
5. `hermes kanban unblock <上层卡> --reason '<简短依据>'`。有未完成 parent 时它会落到 `todo` 而不是 `ready`，这是正确状态：下层卡 done 后由 dispatcher 自动 promote。不要用 `promote` 强行提前。
6. 读回上层卡：status/parents/正文一致即可。`kanban dispatch` 返回 `spawned: []` 且 `promoted: 0` 通常表示 gateway dispatcher 已经并发 claim，不表示未派发——以新 run 的 id/worker_pid 与心跳为准。

保留下层卡的失败 run 与上层卡的 give_up 历史；不重建整图，不动既有 Verify/Review 的 parent 边。拆分只是调度恢复，**不代表工程通过**。

### 绿灯测试不等于接缝证据

worker 常用「import 了真包 / 断言了封装层」冒充「依赖接缝已验证」。判定规则：

- 测试若只调用自己写的包装类而从不进入依赖的真实方法路径，它证明的是包装类，不是接缝。接缝证据必须让**依赖自己的入口函数**在 fake transport 下真实跑一遍（例：真实 SDK 的资金方法由严格 fake 的 signer/provider 驱动，断言签前观察、发送次数 ≤1、异常后 hash 仍保留）。
- 测试若与生产代码平行地手写了一份期望值（dict/JSON），它会与实现的规范化逻辑漂移。**期望值应由生产代码自身产出**（或至少共用同一个归一化函数），否则测试长期红，且修法容易跑偏到削弱生产语义。
- 断言红灯时先判定**哪一侧错**：生产语义与冻结契约一致、而测试辅助函数参数装配错（布尔 flag 当带值参数、手写 dict 字段类型漂移）时，修测试；契约未固定时才讨论改生产语义。把「哪一侧错」写进卡面，别让 worker 猜。
- 「import 真实包 + mock 掉被测方法」不构成实装验证；同层必须有至少一组真实依赖 + fake 底层边界的用例。

### 接缝测试要断言「实际传入的参数」，而不只是「调用发生了」

只断言调用次数为 1 无法发现依赖把参数换掉。必须把**依赖实际发出的参数**也断言出来（用 fake 底层对象捕获），尤其是：当契约要求显式金额而依赖的路由根本不带金额时，断言「该参数没有出现」比断言「调用成功」更早暴露风险。断言失败时先看捕获到的实际参数，再决定是工具层要前置拒绝/补一致同意，还是契约需要修订。

### 依赖制品锁：hash 固定 ≠ 发行版身份

- lock 由**实际下载的本地制品**计算 hash 生成，并断言已安装版本与 lock 一致；再提供一个可重跑的校验脚本（重算并与 lock 逐字节比对）作为独立证据，而不是只在报告里贴一份清单。
- wheel hash **不证明**发行签名、tag→commit 映射或上游下载源；未保存上游 URL 时不得声称已验证发行身份。lock 绑定具体 Python ABI/操作系统，不声称可跨环境安装。
- 安装验证用 `pip install --require-hashes`（可用 `--no-index --find-links` 指向本地制品目录），并补 `pip check`；`pip show` 缺失只证明未安装，不构成缺陷。

### 主控接手实现的收尾纪律

用户明确授权主控接手某张卡的实现时（worker 已回收/被拒），按下面顺序推进，避免又开一条无限探索的长任务：

1. **先定边界再动手**：把卡正文改成「接手授权 + 已核验事实 + 唯一剩余 delta + 禁做事项」，明确「主控自测不等于独立验收」，并把该卡 assignee 改为自己、保持行政 blocked 防止 dispatcher 重复启动同一卡。
2. **不要继承上一轮的形状错误**：若上一轮产出的实现是空壳（例如资金入口永远返回"未执行"），接手时按契约补真实接线，而不是只把红测试改成绿。**让测试变绿但语义仍是 stub，等于交付假完成。**
3. **先写被测路径的真调用，再写断言**：测试要真正进入依赖方法路径；断言同时覆盖次数、顺序、参数与失败后状态。
4. **落一个可重跑的制品校验脚本**，并把每条命令的真实 argv/工作目录/原生 exit/测试计数写进交接与证据文件（unittest 结果在 stderr，不要用管道末端 exit 冒充测试 exit）。
5. **完成时区分实现者与验证者**：卡片 metadata 写明实际实现者为获授权接手的主控，保留不同角色承担的独立 Verify/Review；主控接手 Implement 本身不等于角色分离失效，只有同一执行者兼任本应独立的门禁才算偏离。不要用自己的绿灯替代独立验收。
6. **失败历史不追认**：被安全拒绝的动作保持「未执行」；不得改命令形状或换执行器复现同一探针。交接里把「流程偏离」与「功能结论」分两栏写。

### triage 恢复后仍被 blocker_auth 跳过

恢复原卡到 `ready` 之后，dispatcher 仍可能反复跳过它，日志里只有 `respawn_guarded: reason=blocker_auth`，没有任何新 run。这不是新故障、不是额度耗尽，而是**恢复路径没有清掉的陈旧标记**。

- **机制**：respawn 守卫按优先级先判 `rate_limit_cooldown`（只看最新 run 的 outcome 为 `rate_limited` 且在冷却窗内），再判 `blocker_auth`（在 `last_failure_error` 里匹配配额/认证措辞，且最新 outcome 不是 `crashed`）。限流重排会把配额措辞写进 `last_failure_error`；随后若最新 run 变成 `blocked`，`rate_limit_cooldown` 分支不再命中，那段旧措辞就落进 `blocker_auth`，卡片被永久跳过。triage 恢复（`specify_triage_task`）只改状态，不清该字段。
- **先排除真实额度墙**：在被派发卡片的 assignee profile 上做最小模型探针（`hermes -p <assignee> chat --model <model> --provider <provider> -q '只回复 OK，不调用工具。'`）。探针通过即证明通道可用，陈旧标记是唯一阻塞；探针不通过则按真实额度/订阅问题处理，不要清标记。
- **最小清除路径**：用框架自带的失败计数清理函数（`kanban_db_dispatch._clear_failure_counter`）在脚本内把 `last_failure_error`/`consecutive_failures` 复位，脚本内断言 before/after 并打印。不要写裸 SQL、不改 Hermes 源码、不改 profile/审批配置。
- **命令可用性要先确认**：卡片已经是 `ready` 时 `unblock` 不适用（只接受 blocked/scheduled），`promote` 只接受 todo/blocked，所以「已经恢复成 ready 后仍被跳过」这一形态没有 CLI 子命令可用，必须走上面的框架函数。
- **清完必须 dispatch 一次并读回新 run 的 id/worker_pid**，才称已重新派发；`ready` 只表示排队。
- 清除的是**调度状态**，不是内容完成度：旧的 blocked/rate_limited run 仍是审计历史，不得追认为 PASS。

### 永久 blocked/frozen 的 parent 会永久挡住整条链

下游卡的 `parents=[...]` 只在所有 parent 达到 `done` 时才 promote。把一张**已冻结留证、永远不会再 done** 的旧卡（典型：早期限额冻结的 blocker 卡）留在 parent 列表里，会让整条下游链永久停在 `todo`，而 dispatcher 每次都正常派发「无果」——看起来像调度坏了，实际是状态机前提永不满足。

- **症状**：某张下游卡反复 `todo`，`dispatch` 无报错也不 spawn；`kanban show` 看到它的 parents 里有一张 `blocked`/`gave_up` 的历史卡。
- **修法**：`hermes kanban unlink <blocked_parent_id> <child_id>` 把冻结卡从活链摘除，再 `dispatch`。不要用 `complete` 假装冻结卡已完成——它的语义是“冻结留证”，改成 done 会让证据链失真。
- **预防**：冻结旧卡时同时决定它是否还在活链上；不在活链上的卡建卡时就不要挂进 parent 列表。判断依据是「这张卡还可能被完成吗」，而不是「它是不是我建的」。

### worker 否决卡面修法时，主控必须先复核再接受

worker 在实现中发现**卡面给出的修法与验收标准或数学事实冲突**时，正确行为是否决指令、给出更优实现并留证，而不是照做。

- **不要把“偏离卡面”自动当违规**：先独立复算/复跑，判断 worker 的否决是否成立。
- **典型冲突形态**：修法把某个量算两遍（如费用既在系数里计一次又在权益侧再扣一次），而验收标准要求「只计一次」；此时照做会让实现与断言直接对撞。worker 的解法（把量并入单一系数、权益侧用毛额）往往才是对的。
- **主控的动作**：独立复核 → 确认后 `kanban_comment` 明确认可该否决并写清正确语义 → `complete` 时在 result 里记「正确否决了卡面错误修法，避免双计费」；同时把正确语义**固化成测试**（如「只计一次」回归测试），否则下次仍会被错误“修复”。
- **教训**：卡面给出的“修法”若与验收标准冲突，卡面错。**验收标准才是契约**；这与「指令与数学冲突时否决指令并留证」的验收者纪律是同一条规则，两侧都要认。

### 回收编排 worker 不等于停止其后台业务进程

- 对已启动生产 CLI 的 worker 执行 reclaim 后，分别核验两层状态：Kanban worker 的终止事件，以及已知业务 PID 的精确命令身份、输出目录、summary 和原生退出证据。后台业务进程可能独立存活；不能把卡片 triage、worker terminated 或 PID 字段清空当成业务退出。
- 当前 profile 的 process_manage 对 worker-owned session 返回 not_found，只表示该进程句柄在当前会话不可检索，不证明业务进程不存在、失败或成功。先做已知 PID 的只读身份核对，保留原唯一 apply；禁止为重新获得可追踪句柄而再启动相同写入。
- 回收后紧接 block 可能留下一个零时长的行政 blocked run；以事件 actor、reason、时间和实际业务进程区分，不能把它计作新一轮生产重试。由本次主控登记触发的 triage 通知只读确认一次，不重复 block/comment 或重建图。
- 业务进程尚未结束、summary 尚未生成时，报告“仍运行、当前部分计数、最终结果待确认”，不把实时行数或已保存页数当成完整日验收，也不因暂停编排而丢弃后台进程最终结果的取证责任。

### 纯执行接管与有界续批

1. **先交接原进程结果，再续写。** 核原 PID 的精确命令身份、业务输出与目标状态；PID 消失且有 summary 不足以补造原生退出码。退出码取不到时保留 UNKNOWN，通过既有自然键和实际写入对账判断能否安全幂等续接，不为取得新句柄重复提交旧批。
2. **将接管写入原卡，不重建图。** 在现行正文/镜像记录主控执行、剩余 delta、原预算、停止条件及独立下游，并读回一致。若保留 blocked/triage 只是为防 dispatcher 重复派发，明确区分行政 hold 与业务实际运行；它不解除安全拒绝、生产输入缺口或独立验收门禁，也不能成为无限期不推进的理由。
3. **在主控当前会话启动原显式入口。** 每批使用独立且未存在的报告目录与 `terminal(background=True, notify=True)`，保存 session_id/PID/命令/预算，使完成事件回到真正负责续批的会话。原 apply 未结束不启动第二个；process wait 返回等待窗口超时且仍运行时，不将其当业务失败、终止或重跑。
4. **按完成事件分类，而非把所有非零退出都当失败。** 读取 CLI 的退出码契约、summary 和真实目标状态；区分“本批处理日期均完整、整体窗口尚未齐”与网络失败、冲突、未知写入。核实际 `results` 日期及冻结 manifest 窗口，不只读 `planned_dates`，因为恢复旧扫描可能先完成旧窗。分页数只表示扫描进度，完整日、已存行数与连续完整水位分别报告。
   - **`state=pending` 不等于零写入。** 扫描未闭合的日期可能仍已落库部分记录（分页边界的中间态）；判断增量必须读每条结果的 `inserted`/`updated` 计数和库内实际行数，只看 `state` 会把真实增量误报成“无新增”。
   - **空 `results` 不等于成功或正常分页截断。** 将该来源的空结果与进程 stderr、原生退出及检查点变化对齐；若源级网络调用已失败，保留另一来源的成功增量，但不要套用 `SCAN_NOT_CLOSED` 的正常续传分支，也不要为补出结果数组重复整批写入。
   - **分层解释连通性证据。** 未认证端点返回 401 只能证明取得 HTTP 响应；归档 HEAD 返回 200 不能证明正文可完整下载。只有原认证摄入入口实际获取、校验并保存目标数据，才报告业务取数恢复，不能以探针通过代替这层验证或清零失败退避。
   - **失败分片跨批次累积。** 每个失败日自带 `next_retry_at` 退避且不因换报告目录而清零；判定“本批新增失败”要比对该日的 `last_attempt_at` 是否落在本批执行窗口内，库里仍存在的旧错误标记不算本批新增。
   - **planner 的日期可能领先于冻结窗口。** 冻结的分页扫描窗未闭合时 planner 会给出更晚日期，但执行仍先续旧窗；两者不一致不是 bug，不要据此改窗口或清游标。
5. **按分片裁定停止范围，再续下一有界批。** 本批结果明确、无残留 apply、下一报告目录未占用时，正常预算截断直接按原授权续批，再报告新增实物，不等待用户逐批催促。若部分日期网络失败，先保留其真实失败、原生退出码和 `next_retry_at`，再只读运行既有 planner：只有确认下一计划不包含尚在退避或已耗尽重试的失败分片，且没有全源/全局停止条件，才可继续其它获准日期或可信分页检查点。不同输出目录不使重试计数归零；不得清失败状态、改 due、调大预算或反复运行同一失败分片来绕过上限。未知 ACK、读回冲突、新安全拒绝或认证失败仍按相应动作/来源边界停止；不要把部分失败说成本批全绿，也不要让单个隔离分片的失败无依据地冻结可独立推进的数据源。单批成功不提前 done 或释放要求全窗完成的独立 Verify。
6. **把进度快照与完整内容核验分开安排。** 运行中用有界只读聚合查询取得冻结窗口内的计数、状态和失败分片，不为回答进度启动长时间全量扫描。除非已有快照协议支持并发核验，否则将完整 verify 放在批次结束的稳定边界；耗时未知时使用原核验入口的受跟踪后台执行并保存退出结果，而不是给一个短前台时限后重跑。工具时限截断只说明本次核验未完成，不证明数据错误，也不授予 PASS；另行确认是否仍有原核验进程，避免重复扫描。
7. **每批一条追加式账目，不重复整段进度。** 每批只记：原生退出码、summary 哈希、该批实际处理日期与增量、库内累计快照、失败日及其退避时间、下一批 session/PID。看板 comment 只写该批事实摘要与续批标识，细节留在报告文件；重复整段进度会触发自激通知并稀释关键差异。
8. **对用户报增量而非只报卡状态。** 给出带时区的快照时间、冻结窗口分母的覆盖率、完整日与部分日、实际新增和剩余 delta，并分别说明业务进程与行政 hold。逐来源核对完整日、未完整日及其原因，再总结剩余工作；不要只列推进较快来源的尾段或旧缺口，遗漏较慢来源仍未摄入的历史。来源计划为空时明确区分“目标已齐”与“失败分片尚未到期”，因为空计划不能证明全窗覆盖。按当前 CLI 契约和逐日结果解释退出码：部分完成既可能是本批日期齐而全窗未齐，也可能是分页未闭合或预算截断；不能仅凭退出码 10 断言本批日期齐，更不能写成通过。独立验收未完成前不预告门禁通过，运行中的批次不提前报最终成功。

### 依赖子卡已提前开跑时的回收

子卡被创建时漏传 `parents=[...]`，或依赖关系写在了正文里而非结构里，dispatcher 会**立即 claim 并开跑**，
子卡在输入缺失的情况下开始工作。此时**事后补 link 不能了事**——它已经在跑。按序回收：

1. `hermes kanban reclaim <child_id>` —— 终止当前 worker，把该行退回 `ready`；
2. `hermes kanban link <parent_id> <child_id>` —— 对 `ready` 子卡补链会把它降为 `todo`，
   它下次 claim 时重新检查 parents，故只在 parent `done` 后才真正开跑；
3. 读回整图确认：**只有一张卡处于 running/ready**，其余下游均为 `todo` 且带 parent。

link 的参数顺序是 parent→child；写反会把错误的那张卡降级。

**回收后必须审计共享树的副作用**：已经跑了几分钟的 worker 可能已写入 `workspace_kind="dir"` 的文件。
在子卡被允许重跑前，用 path-filtered diff 对照 allowlist 核对这些路径，把越界产物单列——
“子卡提前开跑”与“子卡写坏了文件”是两个独立事实，不能因为前者被回收就忽略后者。



### 「三处冲突」类文档对齐：先定位行号，再派窄卡

文档卡的 worker 往往在“重新通读三份长文档”上耗尽预算而零产出。主控应先做只读定位，
把每一处冲突写成**行号 + 现行原文 + 期望语义**，再派一张窄范围对齐卡。

- 续接正文必须含：每处的精确文件:行号、现行原文摘录、期望改成的语义、允许修改的 allowlist、
  残留检查的 grep 模式、允许的定向读取次数上限，以及「不得整篇重读/全库 grep/重新核验源码」纪律。
- 跨层对齐后检索全部受影响层，逐条区分现行控制字段与需保全的历史正文；只要求应替换的现行旧表述零残留，不要求历史版本号或退役事故词汇全局零命中，因为这会误改历史身份。
- 版本号不一致时先确定已批准的目标版本：纯对齐修正仍用该版本，核对顶部metadata、来源/关联指针、既有Changelog及历史块之外的末尾“当前版本”字段；不要为漏改字段升下一版本或重复新增版本记录。历史正文和旧版本记录按原契约保全。
- 低风险收口先固定授权单位：用户已批准原文件清单内文字/版本一致性修正时，按该清单与允许语义恢复原Implement，不自设“一行只写”而把每个遗漏变成新审批。
- 恢复前整体替换Implement与既有独立Validate的现行正文，删除相反的“任何新遗漏即停”限制；内联已定位修复及变更边界，要求先修已知字段，再合并剩余低风险修正，最后只补受影响核验。未漂移的有效证据复用，不逐处重跑全套、另升版本或重建链。
- 低风险对齐完成后沿用独立Validate，不把取消重复审批当作降低验收；契约变化、文件越界、生产/隐私副作用与新安全拒绝仍停手，验收者不得代改候选后自签。
- 文档对齐卡完成后，把下游实现卡的依赖从「超时/失败卡」改指「对齐成功卡」，
  并显式 unlink 失败卡——否则实现卡会永远被一块已废弃的门禁挡住。

### 数据批量核对卡的预算纪律（主控写正文时执行）

派 DB 逐格核对、逐 cell 几何校验、全量指标一致性类验证卡时，在正文中写死取证形状，否则 worker 会用 16 次单查询/逐 cell 单脚本把 60 迭代耗在重复往返上：

- **一条 SQL（或一个只读脚本）取回全部行**：逐格单独查询是预算杀手，正文必须给出「单次取回 N 行全部所需字段」的命令形状。
- **一个脚本遍历全部 cell**：几何自洽、模板 diff、指标核对都写成一个循环脚本一次跑完，输出逐行 PASS/FAIL 汇总，禁止逐 cell 单独执行。
- 明确「每个验收项一条命令取证，不重跑」与「证据齐全即收口」。

### 模型恢复的已验证命令形状

先核对本机帮助，再使用：

```text
hermes -p <assignee> chat --model <model> --provider <provider> -q '只回复 OK，不调用工具。'
hermes kanban set-model <task-id> <model> --provider <provider>
hermes auth list <provider>
hermes auth reset <provider> [credential-id]
```

`set-model` 的模型是位置参数，不是 `--model`。对 ready/blocked 卡先更新正文与任务级 override，读回，再恢复；running 卡的 override 通常只影响下次派发，不描述为已替换当前进程。只记录探针结论与适用条件，不将某供应商曾经不可达/可用写成长期事实。

- **先看每个凭据各自的健康状态**：`hermes auth list <provider>` 会列出池内条目的 label/priority 与状态（如 rate-limited/usage_limit_reached）。同池多条凭据时，一条耗尽不等于通道整体不可用；探针成功即证明仍有可用条目，不要因此改 profile 默认模型。
- **`auth reset` 只用于清除陈旧的 exhausted 标记**：仅当失败记录里的原因与当前实际不符（链路层/代理故障被记成配额或认证失败）时，用官方命令清除对应条目的陈旧状态，并先备份 auth 文件。不得用它“逼出”配额限制，不刷新认证、不改凭据优先级或 label。
- **分层证明模型恢复，再释放原卡**：先运行上面的 assignee-profile 最小探针，保存 session id、原生 exit 和正文；再按该 session 精确检索 `agent.turn_context`、成功的 `API call` 与 fallback 记录。只看到配置或正文 OK 不足以确认指定模型服务了请求，因为 fallback 可能代答。辅助标题生成的 429 与主回答分别判定：指定模型成功返回时，不把辅助失败误报成主通道不可用，也不为非必需标题修配置。
- **按证据强度报告恢复**：最小探针通过只称“该 profile 的指定模型当前可达”，不承诺长上下文/工具调用稳定，也不因旧 HTML 403 自动要求重新登录。原路由恢复时保留 profile 与任务覆盖不变；只有获明确换模型授权才设置 override。保留既有范围与父边，更新并读回原卡正文后再 unblock、dispatch 一次；取得新 run 与心跳后，按新 worker session 核对成功 API 调用的实际 model/provider，才称“原任务已用指定模型恢复执行”。日志查询绑定 session id 或完整日期与时间窗，避免短时间模式匹配轮转日志中的旧会话。
- **确认实际产出者**：卡片 summary 不写模型；以成功 API 调用及 fallback 记录确认真实服务模型，再区分内容问题与通道问题。探针或新 worker 失败时保留原失败事实，不用主控自己的成功代替 assignee 证据，不默认改全局 profile、刷新认证或反复重派。

## 3. 恢复正文必须可直接执行

### 复用候选不等于冻结未验证的代码

在把剩余工作归类为「仅补报告/收尾」之前，先读完整剩余 delta，并做定向契约抽查（公开入口是否真执行、不可逆标准化前的保护、计划行集与证据级别、证据保全与验证作者、最终实物规模与授权）——完整清单见 `references/candidate-contract-spot-checks.md`。发现实质缺口就记录为候选未完成，不按行政收尾放行。不要把 worker 最先上报的输入 blocker 当成全部剩余工作；回归转绿、缺输入时安全阻断和完整业务接线是三种不同结论。尤其核对共享 handle 是否贯穿 await 前后、真实累计值是否写入账本、同步/启动恢复是否消费同一事实，避免 helper 已实现而公共入口仍提交默认零增量。

- 候选仅部分落盘或尚未通过原冻结回归时，不得把“不要推倒重写”改写为“只准改消费者，禁止修上游候选”。先核对完整调用链和当前失败；在原 Design/allowlist 内完成必要增量修正不等于重做实现。只有已验证正确的部分才可明确复用并免于重写。
- 续接正文同时列出：已验证行为、仍失败行为、尚缺的原定测试覆盖；测试数变绿不能替代完整验收。每份测试结果绑定候选哈希或明确的改动前后边界；worker 再编辑后，旧的全绿只作历史基线，不继续作为当前候选通过的证据。对每项静态缺口标明尚待动态证实，禁止把自报剩余项当成已通过事实。
- **模型恢复与候选正确性分别校准**：通道恢复后，先复用或取得获准的冻结回归原始输出，再决定剩余 delta 是代码修复还是行政交接。将失败测试名、断言文件:行号、原生 exit 和日志路径内联原卡；这些是定位事实，不是已裁定修法。区分旧 fixture 需适配与真实行为退化，不降低断言求绿，并保留尚未覆盖的原定接缝测试。Rust `cargo test` 若在 lib 集合失败，明确该计数只覆盖已运行集合、后续 targets 未完成，不把命令名称“全量”当成完整覆盖证据。
- 修正解释器或文档身份后，要从 live task body 及镜像中删除相反的现行旧路径/旧哈希，不只在末尾追加覆盖说明；历史限制留在旧 run/交接中。先读回一致的完整新正文，再恢复派发，避免下一轮在互相冲突的“唯一解释器/禁止修改”之间再次自锁。

### 收窄续接范围不制造新的不可满足契约

- **文件工具限制不得与已批准迁位冲突。** `read_file/patch/write_file` 不一定有 move/unlink 能力；任务若要求精确两文件 Move+M 又禁 shell，先由主控核源为普通文件、目标不存在，以无覆盖移动完成已授权的可逆迁位，并核前后 SHA 相同，再把 live body/镜像改为“目标已存在，仅做内容增量”。不清空旧文件冒充迁位，不追加泛化 shell 权限，不为已批准的同一移动重复索要授权；若动作本身遭工具拒绝则仍按拒绝规则停手。路径缺失的 pytest exit 4 只算 collection 阻塞，不是行为 RED 或代码 FAIL。
- **已安装时才运行的工具缺失，不自动升级为交付阻塞。** 先回读原契约对 Ruff 等工具的条件；缺失则如实登记 `UNAVAILABLE/NOT_VERIFIED`，不能写 lint PASS，也不擅装依赖或换环境。其它限定验收已完整且身份一致时，主控可行政完成该切片并向后续门禁同步未验证项；若契约明确强制该工具则仍需解决，不套用此例外。

- 收窄剩余 delta 时，逐条对照原 Design：行为契约（如某类错误必须到达调用方）与文件/函数 allowlist 必须仍然同时可满足，不能为图省事把授权过的上游实现划出范围。
- 文件规模治理只应用现行项目档位和该文件的冻结目标，不把“接近阈值”自设为更严的停工或重做设计门禁。仍在允许档位时，优先在现有职责边界内最小提取、复用测试接缝并记录增长原因，交既有独立审查核对；实际触及架构例外才按契约升级，因为提前制造新阈值会把必要尾项再次变成长设计任务。
- 实现接近全绿时，唯一残留失败可能是续接轮次自己引入的语义漂移（如为收窄而新增的参数/特例断言与冻结的「与改动前无差异」条款冲突）。先用冻结测试复跑并与改动前行为对比，恢复原行为而不是顺着漂移改断言。


- **先自己核验，不要把 worker 自述当事实**。worker 的 summary 是自报，不是证据。先完成上文拒绝扫描与定向契约抽查；只有当前授权允许且不复现被拒动作时，主控才运行候选的必要编译/回归校准。不能执行的检查明确标为未验证，既不能当 PASS，也不能为了取得校准结果绕过审批。结合实际产物、哈希/行数及可取得的独立结果，再决定行政收尾或有界续接；自述与实物/实跑不一致时保留差异。
- **续接正文要分清三类内容**：① 已落盘且已核验的事实（可直接引用）；② 唯一剩余 delta（带精确文件/行号）；③ 禁做事项（不得重写已实现部分、不得越 allowlist、不得真实调用/读凭据）。第③项能直接避免 worker 重新实现一遍已经完成的工作——这是预算耗尽最常见的真实原因。
- **把已定位的根因与证据写进正文**，并要求 worker 只做增量：包括实测命令、实际输出要点（错误码、消息）、源码行号。否则 worker 会重新做一遍探索，而探索正是耗尽预算的主要来源。
- **主动识别“其实不需要 worker 做的事”**：若剩余 delta 只有“核对哈希 → 跑一次固定测试 → 写交接 → complete”，那是行政收尾而非工程任务；主控自己做更快、更可靠。若剩余 delta 含真实代码/研究工作，才派卡。
- **区分“产物齐全”与“产物残缺”的判据是产物本身，不是通知措辞**：预算耗尽通知不区分两者。
  - 齐全：每个应有步骤都有**可定位的落盘输出**（文件路径 + 时间戳 + 可核对的字段），
    且步骤之间**逻辑自洽**（前一步的输出是后一步的输入）。此时只差收尾调用 → 行政收口。
  - 补写缺失的交接/报告文件时，**只做产物索引**：写产物清单、真实命令与原生 exit、测试计数、
    未运行边界、下游入口；不改写 worker 的判定方向、结论措辞或任何计数数字，
    不在补写文件里追加 worker 未做的验证。文件内写明「真实执行者是 worker，行政登记者是主控」。
  - 闭合前用 worker 报告引用的同一份候选/保护 SHA 清单**再跑一次 `sha256sum --check`**（cwd 与 worker 一致），
    exit 0 才证明验收期间输入未漂移；漂移则该报告不得行政收口。
  - 残缺：缺少某步输出、输出为空、输出与后续步骤矛盾、或只存在于 worker 自述里
    → 该步确实未完成，需重跑那一步。
  - 注意区分**有副作用的步骤**与**无副作用的步骤**：无副作用的（如只读查询）可由主控
    重新执行一遍取证；有副作用的（如提交回测 job、创建记录）**不得**为取证重跑，
    直接采信已落盘的产物并登记。
  - 报告中要标明**真实验证作者**（worker）与**行政登记者**（主控）不同，不冒充。
- 固定工作目录、项目解释器和精确 allowlist；本地脚本不混用 PATH Python、Agent 自身解释器与服务后端环境。
- 开头列已完成实物、可信独立证据、尚未完成项与 PASS/FAIL/延期条件。
- 用既有测试集合和普通命令取得必要证据；已有 `sha256sum`、`stat`、`readlink`、测试 CLI 足够时，不为批处理方便另写 runner、扫描器或文本重构脚本。
- 若需修复，合并本轮最小 delta 后运行一次受影响集合；不要每个小 patch 重跑全套测试。
- 预留写报告及 comment/complete/block 的调用预算；证据齐全即收口，不因尚有预算而继续探索。对只写报告的续接，把已定位来源、唯一缺失文件和停止条件直接内联；新 run 先重查这些文件的存在性，因为上次中断前可能已补出部分产物，不能把旧“缺失清单”当作实时事实再生成一遍。
- **冻结续接正文不产生新的证据权威**：worker 收尾摘要、主控转述和卡面引用必须保留来源角色、run/session及证据等级；未配对到原生命令/回执的事实只记“前轮摘要声称”，不能经下游照抄变成“主控已独立核实”。优先引用已绑定同一候选的独立原生日志，不为美化来源重跑套件；合并日志缺少全量输出时明确引用另一个真实全量日志，不能靠表头或摘要补造历史原生退出码。
- 缺少旧文件全文而仅有哈希时，声明证据限制，不逆向重构文本或扫描整个 home/profile 寻找原文；细则见 kanban-verification。

### 前置核实内联与交接优先

- 派长实现卡（墙钟 ≥25min）前，把已核实的只读结论（基线测试计数与 exit、沙箱/依赖 API 白名单、模板关键结构）直接写进卡正文并标注核实者。否则 worker 会用整段墙钟重新发现这些事实，造成零产出超时。
- 内联结论区分「主控已独立复跑」（可直接采信，禁止 worker 重跑）与「worker 上轮核实未复核」（标注待验证）；不把未复核的自报当已核实事实。
- 将「交接优先」限定为先保存真实产物、原始输出与剩余 delta，不是允许提前授予PASS：墙钟将尽而本卡验收未全部满足时，写交接后block；不得complete(done)后在summary中留下未完成项，因为done会自动启动依赖它的Verify/Review。仅当事先已拆为独立验收的窄卡且该卡全部通过时，才登记限定范围PASS，并明确整体尚未通过。
- 复用已有RED测试后尽快写出实现主体；只在fixture与冻结公式确有矛盾时批量修正测试，不连续逐条打磨断言却不落实现。大文件按职责分块写入，不以反复重写同一测试文件替代工程进展。

## 4. 审批拒绝后的分支

- **先按返回语义区分安全拒绝与文件正确性前置检查。** `write_file` 的 `stale_write_blocked` / read-before-write，或 `patch` 匹配失败，若工具明确要求完整重读当前文件再合并，是正常防覆盖/匹配保护，不是安全审批拒绝。按提示完整 `read_file`、保留当前改动并以原文件工具正常编辑，不盲写、不换shell/执行器绕开检查，也不为正常重读请求新授权或把卡block。任务正文的“拒绝后停手”应明确限安全审批/策略拒绝，避免误伤工具自带的恢复协议。真正安全拒绝仍遵循下方停止与授权边界。

0. **先区分「超时」与「无人值守拒绝」。** 超时表示本次审批窗口过期；`runs without a user present to approve` 表示当前无人值守策略未放行该动作，等待更久不等于会弹出可处理的审批。先核对实际被拒工具与对应策略，再决定是否提出命令级规则、受支持的工具级授权或隔离方案；不要断言所有门禁都能由 command_allowlist 解除。两者均不授权换形态重放。若考虑 `approvals.single_query_mode: approve`，必须说明其可能放开其他无人值守审批动作，不能把它包装成 execute_code 专用白名单；项目目录执行模式也不等于操作系统级隔离。权限方案与当前已获准的正常工具续接分别处理，不绑成同一个任务前提。
0a. **反复撞墙时普查被拦的形状，而不是逐次重试。** 拦截事实留在目标 profile 的 `logs/errors.log` / `agent.log*`，捕获组就是 `command_allowlist` 要匹配的 dangerous-pattern key：

   ```bash
   grep -ohi "dangerous ([^)]*) but single-query mode" \
     ~/.hermes/profiles/<profile>/logs/errors.log \
     ~/.hermes/profiles/<profile>/logs/agent.log* \
     | sed 's/[0-9]\+/N/g' | sort | uniq -c | sort -rn
   ```

   计数前先把数字归一化，避免路径与 id 把同一形状打散成多个桶。高频 key 通常意味着**该 profile 从未 allowlist 过这一类**，而不是负载有恶意。
0b. **提案前先证明「加上就能过」。** 直接调用已安装的检测器对比两种 allowlist 下的判定：`from tools.approval_detection import detect_dangerous_command` 返回 `(is_dangerous, pattern_key, description)`，其中 `pattern_key` 就是 allowlist 匹配的字符串。对代表性命令形状跑两遍（现状 vs 候选），得出可归因的判定差异，不靠「应该能匹配」的推断。破坏性形状只放进对比的**被拒一侧**，不执行以验证拒绝。
0c. **提案按口径分组，不把类别键说成窄白名单。** `command_allowlist` 同时接受两类条目：**类别键**（如 `script execution via -e/-c flag`，批准一整类动作）与**精确命令/glob**（只批准具体形状）。类别键放在**无人值守 worker** 上意味着「无人监督地执行任意内联解释器」，与同键放在有人的主控上风险不同——必须单独说明这个差别，不能沿用主控的理由。破坏性类别键（递归删除、find -delete、xargs rm、systemctl 生命周期、SQL TRUNCATE）不列入放行提案；这类高频拦截往往说明任务书写法有问题（该用脚本/文件工具而不是 shell 删除），改任务书比改审批更对。
0d. **改配置前先出横向清单让用户定口径。** 用户说「统一一下」时，先给每个 profile 的对照表（approvals.mode / timeout / cron_mode / hooks_auto_accept / command_allowlist 条目 / 实测被拦次数与形状），让用户选对齐口径，再动手。不要跳到推荐配置。改完需读回字段并确认其它配置未漂移；不声称运行中的 worker 已重载或被阻塞的卡已恢复。
1. 准确记录被拒命令、拒绝原因与未执行的内部子命令，然后遵守工具返回的停止边界；工具拒绝码不是测试进程退出码，不把计划执行的测试、编辑或哈希当成结果。区分审批超时与`runs without a user present to approve`的无人值守限制，但两者都不是改命令形状、换执行器或另派worker完成同一动作的授权。工具要求停止时先等待用户明确恢复授权；获准后才按授权选择原形状重试或普通文件工具/只读命令，并将选择写入续接正文。将执行方式改为可审批路径是恢复措施，不是绕过拒绝的理由。
2. 区分用户的新授权：若明确只批准原命令重试，就限原形状重试一次；若明确批准普通文件工具、逐条原生命令或本地静态脚本，按批准的那一类恢复。用户对紧邻的具体提案回复“同意”，即覆盖该提案列明的对象、动作与方式，不再次索要同一确认；若有多个未决方案才澄清。替代方式须在安全拒绝后明确获准，拒绝前的一般业务授权不能追认绕行；任何同意均不扩为任意执行器、联网、审批配置或业务副作用授权。将被拒入口及其等价包装明确排除，同时把获准的正常入口写进原卡和既有下游，避免下一阶段再次采用同一被拒方式。
3. 将获准的执行方式固化并实际校准，再恢复原卡：
   - 先在现行卡面与镜像列出允许的命令、解释器、脚本精确路径/读写范围和停止条件；同步删除与新授权冲突的旧禁令及文件数量限制，否则新增静态脚本会被旧allowlist再次阻断。只批准普通命令时不另写脚本；明确批准本地脚本时，不再套用笼统的“禁止临时脚本”。
   - 优先逐条执行普通只读命令；复杂文件校验获准后，用文件工具写可审阅、固定输入范围的标准库脚本，再单独运行 `<项目解释器> -B <明确脚本路径>`。只读静态脚本不得引入网络、子进程、SDK、凭据读取或业务副作用；不把多个检查重新拼入复合shell、管道、heredoc或内联解释器，因为外层看似只读不保证扫描器可完整解析内部执行体。该方式仍需经过正常工具审批，不保证必然获准；新拒绝即停止。
   - 主控若已完成获准的输入校验，将真实命令、原生退出码、哈希/计数、输入身份和实际核验者内联交接，供worker直接复用；只补新产物的必要静态检查，不让worker重跑同一输入校准或重读全部源码。输入检查通过不是Design Gate或业务测试通过。
   - 先 `kanban edit` 并完整读回正文/parents/仍阻塞状态，再 `kanban unblock`、dispatch一次并读回新run与运行证据；保留旧blocked记录及原依赖链。JSON 正文被展示器按单行截断时，使用普通 `hermes -p <profile> kanban show <task-id>` 读回分行全文，不将截断预览当作完整核验，也不为可选解析器安装依赖或扩大解释器权限。任务正文须低于当前 worker 上下文的正文截取上限，恢复授权与禁止入口放前部，收口要求不能被裁掉。旧BLOCKED结论标为历史，新授权单列；只读文件访问、静态脚本与测试执行分别按批准范围判断。
4. 不关闭审批保护来解决只读验证；不要把一次拒绝泛化成永久工具禁令。遇新的拒绝仍立即停止并准确报告。
5. 用户取消可选重复检查时，只核验并复用仍适用的既有证据；不换形状执行被取消动作，也不伪称取得一次新验证。
   - **缺的是既有证据引用时，先恢复证据，不重做被拒动作。** 先查任务指定的本地文件；确认未保存所需结果后，用 `session_search` 定位此前成功调用的请求与原始工具返回，保存来源 session/message、精确 ref/版本、真实输出及证据边界，再把本地路径写入原卡正文与镜像。历史恢复不是新取证或解除拒绝；被拒动作继续保持未执行。
   - **按输出的实际证明力续接。** 方法/参数名存在性不能证明 SDK 返回结构、安装制品、运行行为或 tag→commit 映射；HEAD 快照和 release 的 `target_commitish=main` 都不能当固定发行版源码。复合命令最终 exit=0 不能单独证明前段成功，须核前段实际输出/断言标记。证据足够当前需求阶段且未削减契约时，可将明确的制品/API/行为验证留给既有实现与独立验证阶段；设计无法闭合的字段或调用语义仍须阻断，不能以“后续再测”放行。
   - **恢复原卡的非拒绝工作。** 复用已核只读结论，把剩余文档/实现 delta 与禁止复跑的动作写成单义正文；先 edit 并读回，再 unblock/dispatch 并读回新 run。保留旧 blocked 历史和原下游，不为补证重建整条流水线，也不通过改审批配置解决引用缺失。
6. **解除卡状态前先确认该状态支持哪个转换命令**：`unblock` 只作用于 blocked/scheduled，`promote` 只作用于 todo/blocked，`schedule`/`promote`/`specify` 各有白名单；对不支持的当前状态它们会静默或显式拒绝，连续盲试只会留下审计噪音。先用 `hermes kanban <verb> --help` 或读回当前 status 确认，再选命令。
7. **区分"可选步骤被拒"与"必需工作被阻"**：可选步骤被拒时，工作流不应停摆——把被拒动作标为未执行并省略，改用已授权的普通工具完成真正必需的剩余工作；不要为了迁就一次拒绝去改全局审批配置或策略模式。
8. **主控接手实现后，原卡的下游门禁仍要真实存在**：summary/metadata 如实标注实际实现者及接手授权，按上方“主控接手实现的收尾纪律”保留独立角色承担的 Verify/Review，让其读取候选身份与冻结命令；不要将接手自动描述为角色分离违规，也不要将主控自检写成独立验收。

## 4a. 解锁循环熔断（triage 列）的退出路径

同一卡在同一 block kind 上反复 block→unblock 会触发看板的解锁循环熔断：`block_recurrences` 达到上限后卡片被送入 `triage` 列（事件 `block_loop_detected`），且计数跨 unblock 保留。先比较各次实际 reason、候选增量与最新交接，不把相同 kind 当成相同根因：旧输入已解决、后一次仅为实现未完成时，应恢复剩余代码工作，而不是再次索要旧输入或重开设计。熔断是调度保护，不证明代码失败或看板损坏，不运行 repair 代替原因分类。

- **triage 状态不接受 unblock/promote/schedule/reassign，直接 complete 也可能返回 unknown id or terminal state**：不要把它当缺ID或加force重试。唯一受支持的退出是 `hermes kanban specify <task-id>`（或 `decompose`），由辅助 LLM 把卡改写后降为 todo，再由 dispatcher 自动 promote。若用户已裁定只需行政交接，先把原卡正文收窄为只读裁定与登记、禁止重跑实现/测试/研究，再specify；它可能立即被dispatcher派发，恢复冻结正文并精确读回后，若已出现行政worker就让其按窄正文收尾，不强制覆盖活跃claim。登记者按实际角色记录，不因主控启动恢复就写成主控执行。
- **specify 会用辅助 LLM 重写标题和 body**。调用前先归档旧正文，将最新候选、已核事实、必要剩余 delta 和禁做事项写入当前镜像，用 `hermes kanban edit <task-id> --body "$(</absolute/path/current-body.md)"` 写回并精确读回，再执行 specify。成功后立即用 edit 同时恢复原定 title 和镜像 body，读回正文、parents、状态及最新事件。对照 edited 与 claimed 的先后确认 worker 领取的是哪版输入；若 claim 早于正文恢复，须明确通知活跃 worker 使用现行契约，不假定数据库编辑会自动刷新其已加载提示。恢复后只报告已排队或已取得新 run/运行证据，不把 specify 成功当实现通过。
- specify 依赖 `auxiliary.triage_specifier` 配置的辅助模型；辅助链不可用时它会超时或跳过而非改卡——不要把“specify 没生效”误判为卡坏了，也不因此反复重发。但 `--json` 返回 `ok:false` 且 reason 是瞬时 LLM 错误（如 APIConnectionError）时，卡未被改动，重试一次是正确动作；区别于“辅助链长期不可用”（反复超时/跳过），后者才应停止重发。它可能跑满 120 秒以上，放在后台跑并轮询读回状态，不要占前台超时。
- **辅助链长期不可用时，triage 的受支持出口是同一个底层转换。** `hermes kanban specify` 只是辅助 LLM 改写 title/body 后调用 `kb.specify_triage_task`；当 codex 传输错误 + 备用 provider 额度上限让辅助链持续不可用时，直接调用 `kb.specify_triage_task(conn, task_id, author=...)` 可只翻转 `triage -> todo` 并保留正文逐字节不变（调用方不传 title/body 即无字段被改）。这避免让 LLM 重写主控精心冻结的契约正文。调用方式：用 Hermes 运行时解释器 + `PYTHONPATH=<hermes repo>:<PM generation site-packages>` 跑一个小脚本（`kanban_db` 需要 `ruamel.yaml`，store Python 裸跑会 ImportError），并在脚本内读回 before/after 的 status/body/title 断言未变。注意 `promote`/`unblock` 只接受 todo/blocked，triage 状态直接调会报 “promote only applies to 'todo' or 'blocked'”。翻转后 `recompute_ready` 会按 parents 决定是否立刻进 ready/被派发，因此正文必须先冻结成最终契约再翻转。
- **工程与生产输入可分离时，不让已知生产HOLD反复中断离线修复。** 若同卡还有明确未实现代码，而外部writer静默等输入只影响生产执行，恢复正文应内联已验证候选与精确缺口，先完成授权范围内的离线实现/假边界验证，生产分支明确HOLD且不读凭据/连接；不能把这一分离称作前提已满足。离线闭合后只登记`OFFLINE_READY + 生产待输入`并保持整卡未验收，不用done提前释放要求真实数据的下游；工程仍不齐则继续披露NOT_COMPLETE，禁止拿绿色总测试数替代契约覆盖。不要仅因同一个已知HOLD在修复中途反复block→unblock触发熔断。
- **解 triage 前先修真实输入，不要只恢复派发**：熔断后同一原因再触发即证明恢复方式没解决真实输入。常见根因是卡内冻结的执行契约本身有误（解释器名、依赖位置、函数范围）；恢复前先用普通只读命令实测正确值（如 `.venv/bin/python -m pip show`、读源码调用链），把修正写进 Design 与卡镜像，再 specify → 恢复标题/body → 让 dispatcher 重派。修复任务失败 ≠ 依赖未装：先查冻结命令的解释器是否本来就有该依赖的仓库本地 venv。函数范围同理：冻结「仅允许改函数X」与「错误E必须到达调用方」前，必须读调用链——若内层函数已 catch-and-fallback，该 allowlist 不可满足，worker 拒绝伪造是对的；应扩最小 catch 位点或弱化行为，而不是反复恢复派发撞同一堵墙。
- 熔断计数只在 `complete_task` 时清零，unblock 不清。恢复后再次熔断时，按实际原因重锚：同一未解决输入不得原样硬拉；仅有已授权代码尚未完成且有真实增量时，校准候选后收敛剩余实现，不把历史计数误报为仍缺用户决策。正文应要求预算内直接补已知缺口，只有新输入冲突、安全拒绝或预算将尽仍未完成才保存交接并 block，避免刚恢复就因同一待办清单立即自锁。

## 4a.1b 主控侧终端审批也会超时（Hermes runtime）

主控（orchestrator）自己跑 `hermes kanban` 写操作时，同样可能被安全扫描转入审批；审批超时且工具确认未执行时，不当作业务命令失败。用户在拒绝后要求“重发审批”，只原样重发最近仍有必要的那条被拒命令一次，不重发已成功的旧动作、不改变参数或换成脚本。单用途短命令、拆开 comment/create、避免 pipe-to-interpreter 等形状只能在首次发起前设计，或在用户明确批准新形状后采用，不能用于绕过已有拒绝。成功后读取精确目标；再次超时就停，不循环尝试，也不根据后来成功推断此前审批提示已送达。

## 4a.1 看板写入本身也可能被审批门卡住（长中文 + ASCII 混合）

`hermes kanban comment` / `kanban_complete --summary --metadata` 会先过安全扫描。
摘要里同时出现大量中文与 ASCII 标识符（如 `t_b1cc9d44 = PASS`、`+4/-0`）时，
可能命中 homoglyph / confusable-Unicode 规则而进入审批队列；用户未在窗口内响应
即返回 blocked，此时命令**根本没有执行**。

处理规则：

1. 审批超时返回 blocked 时，命令未运行——不要把它当成命令报错或执行失败，
   更不要改写措辞、删减内容或换命令形状去“绕过”。
2. 用户说“重新发我授权 / 重发审批”时，**原样重发同一条命令**即可让审批提示
   再次出现；换措辞会把审批理由变成另一件事，反而无法追认同一动作。
3. 重发前先确认该命令仍是当前需要的动作（状态可能已被别的路径推进过），
   确认后再发，避免重复写入触发自激通知。
4. **首次发起前就采用短 summary + 现行报告路径**：把测试矩阵、命令、计数和候选哈希留在已落盘报告；metadata 只保留下游确实消费的结构化字段，避免同一长交接在正文、summary 与 metadata 重复。若命令已经被拒或审批超时，不得再以缩短摘要、删字段、改措辞或换入口完成同一写入；等待明确恢复授权，按上节重试范围执行。
5. **将工程完成、行政登记和下游运行分开报告**：complete 未执行时，只称“实现及自测已完成、看板未收口”，不称卡片 done；下游任务书落盘不等于已创建或已启动 Verify。恢复授权后先读原卡及 children，再推进仍缺的状态转换，避免重复建卡。

## 4b. 下游与最终交接

### 用户明确要求轻量收尾时，直接改现有链

1. 先读当前 Implement、Verify、拟取消阶段及生产卡的真实状态；用户已明确指定“修复后独立 Verify 即可”时，将本次窄修落实为 Implement → 独立 Verify → 主控收尾，不再请求同一流程决定、不新增 Principal/Design/Review 卡。省略审查不等于省略独立验证，也不自动批准生产写入。
2. 保留正在执行的 Implement 和已有 Verify，只将已授权新增缺陷合并到同一限定修复范围。把定位结果、唯一剩余 delta、受影响模块测试命令和退出条件直接写进卡面；优先一个最终模块回归加必要独立边界用例，不因用户催进度重复探索、重复全仓测试或放大文档交接。
3. 改依赖时，先为生产卡接上保留的 Verify 父边，再归档取消的 Review，最后才移除取消阶段的入边/出边。不要先移除等待父边再归档：dispatcher 可能在两次操作之间发现该卡 ready 并意外启动。读回阶段状态、parents/children 及运行回收事件；若发生短暂 claim，如实记录取消/回收，不把它称为已完成审查或从未启动。
4. 用户同时修正业务语义时，在允许实现新增语义前同步受影响的具体 RFC/SPEC/Design 条款及 allowlist；对明确的局部补充直接修现有三份文档，不把“同步文档”扩成新的设计流水线。同步现行卡面/镜像并通知当前 worker，无需为通知重启 worker。把获准改动文件和契约的新哈希从旧基线等值检查中精确区分，其余候选与历史证据仍须保持原身份。
5. Verify 完成后，主控读取报告、原始测试日志/退出凭据和最终候选哈希，完成限定范围收尾。生产历史覆盖、真实结算证据、检查点恢复及调度是否已完成分别报告；若只差一次明确、可逆且已授权的元数据写入，由主控执行并读回，不另建 Activation 或多层恢复链。

### 已批准的恢复需要文档修订时，先门禁、后原卡续做

仅在现有契约或当前缺口确实要求修订与独立复核时采用以下顺序；不要为普通代码尾项额外加文档阶段。

1. **保留原实现卡的阻塞与失败 run。** 用户批准有界恢复不等于候选已通过；从最后一个成功且可满足的规划父卡创建窄范围文档修订，再用返回的真实 ID 创建独立文档 Gate。不要让修订依赖仍待恢复的实现卡，否则把 Gate 接回原卡会形成环。
2. **先把新 Gate 接为原实现卡的真实 parent，再准备释放。** 使用 `hermes kanban link <gate-id> <implementation-id>`；保留仍有效的旧父卡与后续 Verify/Review，不重建整图。原卡继续 blocked，文档 Gate 的 done 只表示审查结束，必须由主控读取实际 verdict 和开放问题后决定是否放行。
3. **替换现行正文，而不是追加相反指令。** 将批准的剩余 delta、已核验事实、尚未验证候选、证据只读范围和允许的工具写进原卡及现行镜像；把旧镜像显式标为历史并指向新镜像。若恢复改为归档数据离线重现，从现行任务书删除在线取数、凭据读取和旧输出覆盖要求，避免 worker 沿旧命令重做。
4. **冻结新产物位置，保留旧证据的身份。** 明确原始输入、失败结果和开发者自测目录只读，恢复输出使用获批的新目录并在碰撞时停止；不为整理证据删除、搬迁或覆盖旧内容，不把开发者的重现目录当成独立验证。
5. **按实际门禁结果释放原卡。** 先读独立 Gate 的完整报告和最新 run metadata，确认 verdict 与开放问题数量自洽，并实测当前契约 hash；Gate 的 done 不足以放行。通过后，在原卡现行镜像中替换全部 HOLD/待批准措辞，写入最终版本/hash、精确新增及只读路径、剩余 delta、可执行验证和输出责任，避免正文一边放行一边仍要求等待。用 `hermes kanban edit <implementation-id> --body "$(</absolute/path/to/current-body.md)"` 写回；先精确读回正文、真实 parents 和仍阻塞的状态，再单独执行 `hermes kanban unblock <implementation-id> --reason '<简短释放依据>'`，最后再读回同一卡。比较镜像时先检查精确相等；若差异仅为 CLI 去掉的文件末尾换行，可对双方仅用 `rstrip("\n")` 复核并记录，不 strip 正文空白、不重复写卡。释放后若只读到 ready，报告“已解锁待派发”；只有新 run/PID 和运行证据成立才报告“已运行”。保留失败 run 和事件订阅，不轮询等 worker，不因排队而重建卡或重复 unblock。

- 新续接卡的 parent 必须真实存在且能满足；不要挂在永久 blocked 的失败卡上，也不要用占位 ID。
- **父卡 done 只解除依赖门禁，不等于下游已启动**：行政闭合父卡后，下游卡可能停在 `ready` 而无 run。显式 `hermes kanban dispatch --json` 一次，再读回下游卡最新 run 的 id/`worker_pid`/status，才称「下游已运行」；只看到 `ready` 只能说「已排队」。
- 尽量保留既有 Verify/Review 卡，只有依赖失真时才修改相应链接；每次外部状态改动后读取精确目标，确认 body、parents、status 与意图一致。
- 报告给出实际命令、解释器、退出码、测试计数、覆盖范围、候选身份、未完成项与变更路径。直接保存测试stdout/stderr并取得测试进程原生exit；不要用`测试命令 | tail/tee`之后的`$?`报告测试通过，因为默认取到的是末端命令状态。若旧证据只有管道退出码，标为未证实，不追认为exit0。内部subTest不另计为测试方法，包含旧集合的扩展套件不重复累加；缺产物而skip的验收不得计为PASS。
- 普通验收通过则 done；真实缺陷或新拒绝则 blocked。用户明确延期的整体验收可以保持 blocked，并分别记录限定范围结论与 full verdict；不得把延期自动当代码失败或再派修复链。
- 需要主控代登记已完成结果时，标明真实验证作者与行政登记者；没有独立报告或存在相关输入漂移时不得行政授予 PASS，不强制完成活跃 worker。
- 面向用户只说明新增完成项、尚余工作和当前决策点；解除阻塞、换模型或编辑卡片不单独算工程进展。

## 6. 别让“修上游/修平台”变成无底洞

### 多轮恢复仍无交付时，先检查复杂度与投入产出

- 用户质疑耗时或开发量时，先读取最新完整交接及对应源码，把必要开发、候选引入的回归返工、通道等待、流程开销分开说明；只给有证据的耗时，不用大测试计数解释研发缓慢，也不把既有测试冒充新增覆盖。若先前把主体缺口说成“只剩接线/收尾”，明确纠正判断，再列当前最短阻塞路径，不以新一轮任务编号代替实物进展。
- 用户要求最小必须、简单推进时，先把剩余项归为「现行契约必需」「当前目标直接必要」「可选增强」，只执行前两类；按业务闭环顺序将缺口和定向验证写回原卡，复用现有客户端、状态、锁和测试接缝，不重开设计、重做已冻结工具或增加通用框架。把历史探索和证据留在已有交接中，当前正文仅保留可执行增量与必要边界，避免以更长任务书代替简化。若契约本身过重，列出具体冲突供用户裁定，不擅删验收或既有独立门禁。
- 保留来源追溯、精度、幂等、标签隔离、失败不推进完整水位和不误写等正确性底线；通用化、并发快照承诺和复杂公平调度应按实际需求评估，而非一概视为首版必需。
- 复杂度诊断与修改授权分开：建议收敛不代表已获准缩减冻结契约；未经明确决策不得删验收、跳独立门禁或把局部成果标为整体完成。已有正确实现优先复用，避免以简化为名重新开发。

当阻塞的根因在**上游依赖**（平台仓库、第三方服务、网络出口）而不是本仓代码时，先穷尽配置与环境变量手段，
再考虑改上游代码；用户对上游改动面有节制要求时，优先改本仓自己的客户端或参数。

- 改上游前先写清三件事：**为何配置绕不开**、**最小改动面**（精确到文件与函数）、**验证方式**，并取得用户确认。
- 上游改动默认**不 commit/push**，把它当作工作区候选；是否提交、是否回退由用户定。
- 一旦上游改动落地，后续卡（Verify/Review）的输入哈希会漂移；必须把候选哈希写进交接，并让下游卡以该哈希为核对基准，而不是以“当前工作区”为准。
