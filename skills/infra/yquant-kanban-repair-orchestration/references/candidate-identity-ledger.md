# 候选身份清单治理：让 Implement → Verify → Review 共用同一条证据链

适用于多角色流水线（Implement → 独立 Verify → 独立 Review）共用一个 `dir` 工作树、且中间存在多轮修复的工程任务。目标：任何一轮都能回答“被验收的到底是哪份字节”，而不靠叙述。

## 为什么需要清单而不是叙述

共享工作树里同时存在三类字节，它们必须分开记账：

1. **候选字节**：本轮允许改、且被验收的文件。
2. **受保护字节**：本轮不得改的文件（策略公式、策略配置、依赖锁、其它模块、三层契约文档）。
3. **历史证据字节**：上一轮已产出的报告与交接文件。

把三者混在一份清单里，会出现两种典型伪证：一是按当前字节重算全部 SHA 来“确认一致”，从而把越界改动洗成合法；二是为了让旧报告对得上而覆盖旧报告，断掉下游按路径取证的引用。

## 四份清单的分工

| 清单 | 内容 | 生命周期 | 谁写 |
|---|---|---|---|
| `source-before.sha256` | 修复前覆盖本轮可能触碰的全部路径（含只读兼容路径） | 一次性，作“修前基线” | 主控在派 Fix 前 |
| `protected-r1.sha256` | 受保护路径，SHA **沿用修前值**，不改写 | 每轮修复更新一次 | 主控 |
| `candidate-final.sha256` | 本轮候选字节 + 工具/依赖制品身份 | 每轮候选定稿后一次 | 实现者 |
| `historical-reports.sha256` | 上一轮报告与交接文件 | 每轮结束一次 | 主控 |

## 解冻规则：允许变更的路径只能“减去”，不能“重算”

当某一轮明确授权修改某条原本被冻结的路径（例如工具层的两个文件），做法是：

- 新清单 = 旧保护清单**减去**这两项，其余项的 SHA 值**逐字沿用旧清单**；
- 绝不允许对其余项按当前字节重算 SHA——那等于把漂移合法化；
- 复核时独立读旧清单与新清单，逐项比对“减少的恰好是获准项”，而不是只比数量。

同样地，某轮授权变更不意味着其它轮次也授权；每轮都要有自己的解冻说明，不能沿用上一轮的解冻。

## 漂移检查的正确位置

在**每一轮门禁收口前**，用该轮报告引用的同一份清单再跑一次校验（cwd 必须与写入该清单时一致——仓库根清单与子模块清单 cwd 不同）：

- exit 0 → 验收期间输入未变，该报告可被行政收口；
- 非 0 → 输入漂移，该报告**不得**被收口，必须先归因漂移来源（谁、何时、哪个路径）。

这条检查成本极低，却能挡住最常见的伪 PASS：worker 跑完测试后共享树又被别的卡或主控改动，而报告仍被当作当前候选的证据。

计数口径：报告里同时出现的多个校验清单要分别写行数与含义，不要相加成一个“已核验 N 项”。

## 历史证据只追加，不覆盖

对已有报告的修正一律新建追加式勘误文件（见 SKILL.md「验收报告自身的事实错误」），并在 `historical-reports.sha256` 中保留被勘误文件的原字节。勘误文件本身是新一轮的候选输入，必须被下一轮门禁正文显式指向。

## 交接文件里的最小账目

- 执行者与行政登记者分别是谁；
- 四份清单各覆盖什么、cwd 在哪、exit 多少；
- 本轮唯一全量计数（过滤组是全量子集时明确写“已含于全量，不叠加”）；
- 冻结工具/依赖制品的身份（wheel、lock、ABI 等）；
- 哪些字节只有修前 SHA 而没有逐字历史 diff——如实写“证据限制”，不要逆向重构旧文本。

## 常见失败

- 只对 untracked 新文件做 `git diff --check`：不覆盖 untracked，需逐文件 `git diff --no-index --check /dev/null <path>`；该命令带差异退出码语义，返回 1 且无空白诊断不等于失败。
- 用 `kanban list --json` 判断当前卡状态：list 混入其它 tenant/项目且体积巨大，一律用 `show <id> --json`。
- 把“解冻两项”写成“更新全部 23 项 SHA”：这是掩盖漂移，不是保护。
