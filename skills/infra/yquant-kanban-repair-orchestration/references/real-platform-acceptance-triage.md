# 真实接入验收的失败归因

适用场景：跑真实平台闭环（回测、参数进化、数据取数、UI 读回）时客户端报错或退出码异常。目标是把失败归到**客户端缺陷 / 平台已成功 / 上游数据故障 / 凭据缺失**四类之一，再决定动作。

## 归因顺序（不要跳步）

1. **客户端崩溃时先查平台是否已成功。** 客户端在校验或读回阶段崩溃，平台侧作业可能已成功并持久化。先查平台的既有记录端点（回测历史列表、进化 job 列表、单次 run 读回）取真实 runId/jobId 与结果，再决定是否重跑。跳过这步会重复消耗预算，并把"平台早已成功"误报成"从未成功"。

2. **未捕获异常优先于环境归因。** 客户端抛出未捕获异常（如 `ValueError`）说明退出码已失去契约含义（不再是业务退出码），且报告通常不落盘。这是真实缺陷，必须按最小修复卡处理，不能笼统写成"环境问题"。先定位失败点，再决定委派还是修环境。

3. **凭据缺失有独立签名。** 认证缺失通常返回专门的业务码/退出码，与崩溃分开判定，不要混为一类。

## 平台数值字段常是十进制字符串

平台持久化的数值字段（初始资金、费率等）常以十进制字符串返回，例如 `"10000.00000000"`。

- 读回比较用**浮点容差**：先 `float()`，再比绝对差（1e-9 量级）。
- 不要用 `int()` / `str()` 直接转换平台值：`int("10000.00000000")` 抛未捕获 `ValueError`。
- 百分比字段（收益率、最大回撤）本身已是百分数，不要再乘 100。

这类缺陷的最小修复仍走 developer 卡 + 独立 tester 回归；主控不自行改生产代码（除非属于零语义的机械收尾）。

## 平台「按设计拒绝」是独立的一类失败

平台可能在新任务开始前就按其内部合约拒绝请求（进化任务报 `observationRangeTooShort`、
`walkForwardUnavailable` 等），既不产生业务结果也不消耗回测预算。

- 这类失败**不是**客户端缺陷、不是上游数据故障、不是凭据缺失：平台侧作业状态为
  failed 且 `actualBacktestRuns` 为空，说明它拒绝的是**请求参数组合**本身。
- 归因方法是读平台源码把拒绝条件写成可复算的算式（最小样本数、最小折数、
  参数上限等），再用本次请求的真实取值代入，而不是反复重试或换数据源。
- **提交前先算**。凡是平台会按合约拒绝的高成本操作（参数进化、批量作业、
  长窗口回测），先把拒绝条件写成算式核对；预算有限时，一次被拒就等于用掉唯一机会。
- 若拒绝条件来自「已冻结的公开契约」（窗口、warmup、folds、成本、硬约束），
  修复方向是**重锚契约并取得用户裁定**，不是本地放宽断言或换更宽松的参数硬闯。

## 客户端对平台返回字段的「存在性假设」会静默禁用功能分支

客户端若假定平台响应里存在某个字段并据此判定能力（例如「有 X 字段才允许搜索参数」
「列表里含某 product_type 才算资金费不适用」），而该字段实际只对某一类标的返回，
结果是对所有其他标的永久走跳过分支——功能看起来"正常跳过"，实际从未被调用。

- 平台**缺省给出能力**时，判定语义应是「只有显式否定才撤回」，而不是「没有肯定标记就拒绝」。
- 判定某项不适用时，依据必须是**该标的自身可读回的身份证据**（市场、品种类型、
  杠杆开关、清单标志），不是某一类标的专属的目录列表。
- 离线 fixture 必须复刻真实响应的**缺省字段形状**：给 fixture 补上真实响应里不存在的字段，
  会把契约缺陷伪装成通过。回归要覆盖「真实响应里该字段不存在」这一情形。
- 每次真实接入后回读一次该功能分支是否**真的被走到**（有 jobId / 有提交记录），
  而不是只看流程正常结束。

## 上游数据故障与数据真空要分开

行情/数据端点返回"无数据"时，业务层文案会遮蔽真实原因，必须下钻服务日志定位 provider 级错误。

- provider 报 TLS/连接类错误 → 上游或代理链路问题，与"确实没有这批数据"是两回事。
- 逐进程确认代理等环境是否真的注入到服务进程（读 `/proc/<pid>/environ`）；已注入仍失败，指向代理节点或 TLS 路径本身，而不是"进程没配环境"。
- 依赖历史快照的运行可能仍然成功：**数据端点坏了 ≠ 业务链路坏了**，两者必须分别陈述，不能互相推导。

## 多批数据同步：先核缺口，再裁定恢复

用户要求整体排查时，按以下顺序一次取证，避免把重复续跑误当收口：

1. **定义固定窗口与分母，再枚举批次。** 使用显式UTC半开边界，程序化收集全部summary并保存路径/hash；识别首批目录别名，不从编号连续性猜缺批。分别累计inserted、updated、skipped，核“本轮前基线＋真实新增＝当前实库”。原生退出不在summary时另查执行记录，取不到记UNKNOWN，不凭文件存在补认成功。
2. **实扫时间槽，再对照日账。** 用实际自然键唯一索引与每日count/min/max/时间对齐核完整性；对部分日枚举精确缺口区间。分别列出“整日未存”“部分已存”“记录齐但标签不合格”，不要把所有非complete日统称整日缺数。多源分别统计，并另外计算交集完整日与从锚点遇缺即停的连续水位。
3. **逐层核闭合前提。** 对照业务行、日/分片状态、原始manifest引用、摘要、枚举水位和完整水位。逐条读取受影响分片的真实引用，再检查回查后的提交分支；行修复成功不保证日状态会重算，缺manifest可能使恢复停在“行已补、分片未闭合”。不要只根据修复函数存在就宣布整链可自动闭合。
4. **验证归档的含义。** 去重后核每个关联原档的字节hash，归档源另核官方checksum、成员及CRC。明确区分“原档字节可追溯”“记录结构/槽位正确”和“全部业务字段已对原文语义重放”；前两者不能替代最后一项或独立生产验收。
5. **核计划是否真的无工作。** 将存储due、操作员可复核状态、当前时刻、显式窗口与流锚点一起代入既有planner。固定历史计划为空，不代表最新完整日无需增量；默认只读plan也未必传了实际apply使用的锚点。比较两条入口的真实参数后，才能宣称规划等价。
6. **分清请求、分片与记录三层退避。** 将请求内有限重试、日级next_retry_at、按ID的next_check_at分开核；本地冷却不是官方封禁。对递增退避用纯内存时钟分别测试准时、迟到、跨重启调用，不能只信docstring。探针证明旧行为有误，不代表新恢复策略已经实现或获生产验证。
7. **按真实调用路径核无人值守接线。** 人工命令临时注入凭据成功，不证明启动模板或调度进程也具备同样输入；裸进程未获得变量，也不证明调度器一定缺失。只报告存在性/解析结果，不输出值。区分已验证的运行时读取方式与尚未验证的长期配置，不把会被自动清理的临时文件当永久部署来源。
8. **提交一个分层结论和最小收口顺序。** 分为确实缺数据、已存待闭合、已证实实现缺陷、条件触发风险、未执行验收。条件风险须写触发前提，不能包装成当前故障；工程修复尚在运行时，不把新增参数或策略记录成已验证的恢复命令。正文给精确缺口表和优先动作，逐批明细与全日矩阵放报告附件，不再逐条重发流水日志。

按ID回查、正常分片重枚举和显式人工复核可能是不同的合法恢复路径；先核各自前置条件，不把某一路径的due时间误写成所有恢复的唯一合法时刻。任何缩短冷却、重扫、标签更新或调度变更仍按本次明确授权执行，不由只读审计顺手激活。

## 重跑纪律

- 归因为客户端缺陷时，先修再重跑；不要靠放宽断言或改口径让失败消失。
- 归因为平台已成功时，复用既有 runId 继续后续步骤，不重跑已通过的阶段。
- 归因为上游故障时，向用户明确列出可选项与各自影响，请其授权涉及服务重启/配置变更的动作，不要自行重启业务服务。
