# 过重契约的替换流程

适用：用户裁定“设计/方案太复杂，按最简单的方式做”，且被否掉的是**已冻结契约本身**（故障分类表、退出码矩阵、旁路记录、漂移检测、探针协议），不是措辞。

## 为什么不能沿用原卡

旧卡的 body 里仍写着被否的契约。下游 worker 每次开工都会重新读它并重新实现那套分类表。后果：每一轮都消耗一次完整 worker 运行，产出一轮修订循环，用户反复看到“还在改文档”而不是修复本身。

## 一、先找最小充分信号

多数运维故障只要一个廉价可观测量就能定案：

| 故障 | 最小信号 | 被否掉的过度设计 |
|---|---|---|
| 服务包装器不随子进程退出而失败（服务显示 Running 但无监听） | 该端口是否有人监听 | 状态分类表、地址漂移检测、协议探针、旁路记录格式 |
| bind 目标地址在启动时不存在 | 目标地址是否出现在网卡 | 网段推导、地址族枚举矩阵 |
| 依赖未就绪 | 该依赖的本地端口/健康端点是否响应 | 状态机、阶段编号体系 |

规则：先证明最小信号能满足当前行为目标，再决定是否需要更多分支。没有当前需求或风险证据的增强，从首版强制契约移出；已正确且有覆盖的实现不机械删除，以免简化变成返工或回归。

数据工程也按相同原则选择证据，而不是照搬运维的单一健康信号：

| 目标 | 当前最小充分证据 | 不默认升级为必需能力 |
|---|---|---|
| 有限集合非破坏复制 | 明确源/目标清单、实际内容/索引/options/TTL核对、冲突不覆盖、源漂移可见 | 任意集合通用迁移框架、强制外置摘要索引设施 |
| 有限写入窗口 | 已知写入口/责任者、操作者窗口内不并发写的确认、源前后与目标内容核对 | 所有外部 writer 绝对不存在的证明、签名/时效令牌体系 |
| 固定来源历史采集 | 官方 raw/checksum、精度、自然键幂等、有界续跑、真实缺口与状态 | 通用多源公平调度器、独立任务 runtime |
| 稳定窗口研究读取 | 时间范围/来源/内容摘要、特征标签分离、可得时间及假设声明 | 并发写条件下严格快照保证、逐页重复摘要、通用消费确认协议 |

只有用户已批准这些使用前提和范围收敛时，才替换旧强制条款；源有漂移、实际结构不支持或内容核对失败仍须停止。稳定窗口读取不能被宣传成严格 point-in-time 或实盘等价。

## 二、权威清单怎么写

一份冻结清单，四段：

1. **改哪些文件**（精确路径，逐个列出）
2. **按序的步骤**（每步一句，含判定依据）
3. **常量**（每个常量写明作用对象 + 可观测效果 + 边界）
4. **不做清单**（明确禁止出现的能力，逐条列）

禁止：留下没有作用对象的常量；留下“必要时再判断”的分支；留下为了写日志而设计的第二套输出格式。

## 三、派卡前自检（防止 worker 用一次运行发现你写错的矛盾）

| 矛盾型 | 表现 | 预防 |
|---|---|---|
| 禁词 vs 必写 | 验收要求全文不得出现 token X，body 又要求 changelog 写出 X | changelog 改用不含 X 的表述，或显式给唯一豁免行 |
| 常量悬空 | 设计章节列了常量 C，但冻结步骤与下游实现卡都没有它 | 常量必须写明作用对象；无对象的常量直接删除 |
| 禁止 vs 验收 | “不得修改 X” 与验收要求修改 X 同卡并存 | 派卡前逐条对照验收清单与禁止清单 |
| 阶段编号 | 步骤表与正文叙述用两套编号 | 只用一套编号，并要求两处同步 |

命中任一条，在派卡前改口径；不要让 worker 用一次运行去发现。

## 四、换链与隔离

```
M1 最小文档(principal) → M2 实现(developer) → M3 验证(tester) → M4 审查(reviewer)
```

- 每张卡内联同一份短裁定并指向完整冻结文件；勿复制整份历史契约或日志，长上下文会遮蔽本卡唯一差分。创建后将 live body 与镜像逐字核对，不把文件写好等同看板已更新。
- 先按阶段语义画必要边，再逐张创建并保留真实 ID；使用 `--idempotency-key <稳定业务阶段键>` 防中断重建出重复卡，仍须读回 scope 与 parents，命中去重不代表旧卡正文已正确。
- 若旧卡仍在运行，先 `reclaim` 并确认终止，再冻结；旧链卡不删除：状态允许时 `kanban_block`（附替代链 id）；`todo` 状态下 `kanban_block` 会被 API 拒绝，改用 durable `kanban_comment` 写 “SUPERSEDED / DO NOT DISPATCH: replacement chain = …”。
- 旧链若已 `blocked`，保持 blocked 并加 comment；不要为了让看板变绿而解除。
- 旧链的 `todo` 后代依赖未完成父卡才不会被 promote；隔离时确认这一点仍然成立。

## 五、分别定义工程与执行交付

当用户批准将过大的整体验收拆为独立交付时：

1. 工程卡只修改最小差分并取得既定独立验证/审查；真实迁移、抓取或回填卡只执行已审 CLI，不在生产执行卡里顺手修代码。
2. 将凭据准备、操作者短窗口确认等事实留给实际需要它的执行节点，不让这些输入反复打断可分离的离线修复。若事实尚未具备，执行节点先创建为 blocked 并绑定真实工程前置，不派空 worker 去发现同一缺口。
3. 分别登记工程可用、迁移已核对、历史覆盖、每日入口已实跑和调度已读回；原整体验收尚有未完成目标时继续明确披露，不能把拆分交付包装成全部完成。
4. 历史数据分列价格覆盖、轮次枚举覆盖与官方标签状态；记录已保存不意味着官方已结算，pending 不是可伪造的标签。
5. 已有代码/测试较完整时，先一次冻结回归校准，再只修新契约下的剩余差分。不要每个小 patch 重跑完整 suite，也不要沿用编辑前绿色结果作编辑后通过证据。

## 六、汇报方式

给**契约的差量**，而不是只报新链：

- “已删除：故障分类表、退出码矩阵、地址漂移检测、协议探针、旁路记录格式。”
- “现在只靠 X 判断健康、只靠 Y 判断坏掉。”
- “唯一写动作是 Z，其余全只读。”

用户判断复杂度是否真的降下来，靠的是这份差量，而不是建了几张卡。

### 6.1 简化到最小后，先用对照实验定案再改文件

被否掉的常常不只是**机制数量**，还有**判断方式**。收敛到最小信号后，必须先证明这个信号真的能区分两种状态，否则简化只是换一种可能错的方式。

- 对每个最小信号，写一组**可在本机复现的对照实验**（各变体一条命令 + 期望退出码/状态码），先跑出结果，再改生产文件。
- 平台语义类推断（命令行参数如何被解析、进程为何立即退出、开关残留如何影响全局）**必须**有同构对照实验；纯推理改生产脚本，很容易在改完两轮后才发现根因判断错了。
- 区分三种含义：找不到命令 / 立即正常返回 / 被超时杀掉而本应阻塞。“立即退出”在长驻场景里是**失败签名**，不要读成正常结束。
- 实验命令要无副作用；需要审批时先取得授权，超时即停，不换执行器绕过。
- 改动后用**反向重建**证明差异范围：把新行替回旧行重算哈希，应还原改动前版本；这能排除“顺手改了别处”。
- 简化后的方案同时要满足用户口述的**行为目标**（例如“代理不自动启动时系统也要能上网”），而不只是技术上的最小改动；把行为目标写成一句可判定的验收语句，再据此选实现。

## 七、边界

- 简化不得越过已授权的生产边界：真实重启、真实冷启动、权限变更仍需单独授权。
- 简化不等于跳过独立验证：Implement → Verify → Review 仍由不同角色承担，Verify 仍为只读独立运行。
- 简化后的实现仍要保留原有脚本/组件的既有职责（参数、命令、日志格式、失败语义），不能因为“简单”把别人的职责丢掉。
