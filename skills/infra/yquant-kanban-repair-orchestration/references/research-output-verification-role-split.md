# 研究类产出的验收角色分工与检查项规模控制

适用于「研究/分析类产出」的一次性验收（如多窗口研究汇总表、风险判定重算、指标载体）。
与「代码缺陷修复链」（见 SKILL.md 主文）不同：这里没有代码 bug 要修，只有一份产物要证明它对。

## 一、角色分工：单角色验收，reviewer 按窄触发条件才开

| 角色 | 职责 | 启用条件 |
|---|---|---|
| 实现 | 按已冻结契约做最小实现 | 有代码改动 |
| 验收 | 独立重算对拍 + 载体同源核对（+ 口径/范围一致性，按触发条件） | 研究类产出后**必过** |
| 复审 | 只审契约文档与实现/报告三处一致性、审 diff 范围、出通过/退回决定 | **仅**同时满足：改了多层契约文档 **且** 变更涉及交易/风控语义 |

**关键裁定：研究验收归 Light Flow 的 Verify 阶段，单角色完成，不为研究场景额外加角色。**

理由三条：

1. **独立性来自两件事，不来自角色数量**：「实现者不是验证者」+「验证者不用实现者的算法」。
   同一数值用同法重算两次不构成额外独立性——两次都写错同一个公式时，双 PASS 反而更危险。
2. **研究线没有「合入」动作**。复审的核心产出是「通过/退回决定」，在研究场景里这个决定
   就是验收结论本身，职责重叠而非互补。
3. **成本**：每多一个角色就多一轮调度 + 一次 worker 启动 + 一次共享树写风险，
   而收益为零。

**窄触发条件的两个要点**：

- 「改了多层契约文档」指 RFC/SPEC/Design 这类冻结契约正文，**技能文档（SKILL.md）自身的修订不算**——
  技能是操作说明，改它不改变被研究对象的业务语义。
- 「涉交易/风控语义」排除纯阈值、纯展示口径、纯列序类调整。
  纯数值研究（换合约、换窗口、加 cell）同样不触发。

不触发时**不要补开复审卡**：那会让后续会话误以为「研究验收必须有复审」，把流程固化成纯形式。

## 二、对拍基准必须由第三方产生并双路径交叉

验收者现算基准 = 验收者沿用实现的假设，独立性归零。规则：

1. 基准由**非实现者**（编排层）预先独立算好，把**具体数值 + 容差**写进验收卡正文。
2. 基准必须**双路径交叉**（闭式解 + 暴力扫描/网格逼近），不能只有一条——
   单条基准若本身有误，会与实现「一致地错」而双双通过。
3. 基准与实现不一致时，先判定是「实现错」还是「基准错」，两者都可能，**不得默认以实现为准**。

对拍时最容易踩的数学坑：**双计费**。若费用已在维持保证金系数里计过一次（如 MF = MMR + close_fee），
权益侧再减一次就是双计费。独立重算要按冻结契约数一遍计费点，别照抄实现的符号。
另一类坑是**隐式口径**：旧发布值可能本就用了某口径，所以「数值零漂移」不代表语义已冻结——
零漂移时仍要用测试锁死口径，防止未来被错误"修复"。

## 三、检查项数量直接决定验收成本与形式化程度

检查项越多，每项都要消耗 worker 一次推理与一次脚本运行，且部分项会退化成勾选仪式。
控制规则：

- **每项必须可证伪**：写成「相对差 ≤ 1e-9」「drift = 0/N」这类可计算判据；
  不写「检查一致性」这类无法判定真假的措辞。
- **每项必须不能被同一实现同错地通过**：只测「实现自洽」的项（格式、字段存在）可并入其它项，
  不单列、不单独计时。
- **按需触发**：只有当本次变更命中某类风险时（如口径/阈值/契约/公式语义变更）才要求该项，
  否则它是纯形式。测试执行这类项由实现阶段负责，验收阶段不重复跑全量。
- **合并优先于新增**：专项扫描、语义核对、范围审计这类独立项，若能并入主检查就并入，
  并在文档里写明「已并入第 N 项，不单列检查项」。

经验规模：3 项左右、2 次脚本运行即可覆盖绝大多数研究验收场景。

## 四、验收纪律

1. **只读**：不改实现、不改断言、不重算覆盖已发布数值。
2. **只报证据**：发现分歧只记录期望/实际与复现命令，不动手修；修复另起任务。
3. **指令与数学/验收标准冲突时否决指令并留证**——以验收标准为准，不以卡面修法为准。

## 五、旧检查清单退役时的映射留档

当一次验收实际执行的是旧格式的 N 项清单，而标准已改为 M 项，**不要让两套并存**：

- 在证据目录补一份映射说明，逐项写清「旧第 N 项 → 新第 M 项」的归属与判据是否变化；
- 特别写明被并入的项（专项扫描、范围审计）与被移除的项（重复执行测试），
  以及移除的理由（成本与重复计时，不是判据被削弱）；
- 若某项从独立项降级为「并入主检查」，要写明主检查已覆盖它的判据，
  避免后来者以为该判据丢失了。

映射说明是文档活，不是事故记录：文件名用「主题 + 日期」，不用任务 ID 命名。

## 七、把研究验收作为下游进化的门禁

研究结论选出候选后要进入策略进化时，研究验收不因“进化已完成”而免除：原生进化产出的候选
仍须过同一套研究侧验收（风险包络、回撤上限、强平压力测试价格未穿越），合格者才进入最终比较。
平台原生排名不认识研究侧阈值，原生评分首位不等于研究结论。

对比报告必须给出**进化前基准的同口径逐窗口逐指标**，否则无法回答「进化是否真的改善」；
缺基准数字的对比报告不构成交付。

## 六、结论格式

```
结论：PASS / FAIL（二值）
证据：对拍结果一行 + 同源核对一行（命令 + 输出摘要）
未覆盖：一句话
```

存在未闭合的 FAIL / major 一律 FAIL。PASS 必须写清覆盖范围与未覆盖项
（如外部接口降级路径只由单测 mock 覆盖、本次实测走的是快路径），
不把「本次走的是快路径」说成「该路径已验证」。
